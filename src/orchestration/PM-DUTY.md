# PM 值班说明

何时读：调度器唤起你时，每次都读。拉起工作由调度器做，你只做判断。读完就开始：不通读 PM 规则，不搜索项目，不读工具源码；某一项要判断时，再按需读那一项的规则。

1. 运行接续：`python3 matrix/orchestration/tools/pm_tasks.py --project . --command <命令文件>`，内容为 `{"op":"continue"}`。
   有 `stage_line` 时直接用作回复的项目阶段行，不再按本轮动作数或 PM 工作流数阶段。运行暂停、额度用完等 `runtime_state` 另列为恢复条件；不将就绪未启动的任务改称等人审。
2. 按 `actions` 逐项做。每项附有 `command`，已填好任务当前的 revision；按你的判断改写其中尖括号的部分再执行。几项可以合成一个命令列表，一次执行。做完后重新运行接续。
   - `pm` 中的 review：按判据检验交给你的成果，填 outcome 与检验记录。adopt：核对后采用；要人审的，动作里附有人审的来源与原话，先核对再采用。
   - `pm` 中的其余各项（结束未交出、受阻、依据已变、检验没过、超时、超过上限）：先看动作里的 `last_run`（最近一次运行怎样结束），再决定重做（command 把任务放回 planned）、改派（reassign），或交人（`or_hand_to_person`）。重做解决不了的（例如模型不可用），直接交人。
     检验没过时，command 使用 `plan_restart`：填写本次返工依据及要求的归因，调度器读取记录后启动；参数与边界见 [任务工具](TASK-TOOL.md)「检验、人工决定、上报、转交」。
   - `inbox`：人说的话；带 `ref` 的，是关于那项任务的答复。新需求按 [反馈规程](../base/FEEDBACK-PROTOCOL.md) 合批，走变更；答复按 `ref_task` 的当前版本应用到对应任务：只移除已解决的 awaiting，按需要登记确认、恢复或返工，再执行 command（inbox_done）。答复明确允许后续工作时，先把该工作登记到任务表并核对可用输入；不能开始的登记具体阻碍及接续责任，不以原 actions 为空代替这一步。仍有未决事项时留下具体内容与原因。只把收件标为完成不会解除任务等待；"继续"只恢复既有授权。
   - `derive`：按已确认的实例配置派生（command 已写好配置项），再把执行者记到任务上。
   - `milestone`：由你登记实际阶段协调的启动回执，展开工作任务并用 completion_requires 登记阶段完成前置；阶段本身不另开执行进程。关联工作交回时核对阶段完成条件，再提交阶段证据和检验。
   - `checker`：安排具备相应专业能力、职级与独立性的检验者；现有配置不够时登记具体待决配置，不重复派发已被拦截的自审，也不由 PM 代专业判断。
   - `resource`：先查项目资源目录，按实际依据更新 `project_config`；缺事实时登记向谁核实，不把待核实改成可用。独占资源正常排队不需要重做任务。
3. 要人决定的事（例如要改实例配置、要真实审定），在任务上记 awaiting。收件只是模拟、授权无法核实或缺少真实答复时，也登记关联 ref 的跟进事项、缺口和接续责任人，保持待核实；这项登记不代表批准或启动。原任务已完成则保留完成状态，另建待核实的后续任务，不重开原成果。登记缺输入前实际打开 ref_task 所引用的输入与证据：未读写待核对，路径不存在写缺失，内容不足则写具体不足，不把这三种情况合并为不存在。回读接续确认缺口可见后结束，不能只在回复里请人补充。
4. 要看一项任务的细节，用 `{"op":"task","id":…}`；要找条目，用 `{"op":"find","text":…}`。不读全量状态与流水。
5. 没有 `actions` 就结束。视图由调度器重建，不必自己渲染。
6. 守住职责：不代专业检验与采用，不替人批准，不凭记忆办事，以任务表为准。

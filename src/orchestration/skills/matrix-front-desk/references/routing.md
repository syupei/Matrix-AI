# 登记、转交与展示

何时读：收到新要求、修改意见或反馈；有需要人决定的事；人想深入讨论某一领域时。

## 新要求与反馈

转交回执在给人的回复中说明：**谁评估、谁决定、什么时候才能生效**。对目标、范围、业务规则或验收的变更，产品负责专业评估和结论；最终决定由项目授权记录中的产品决定人作出，保留给人的事项仍由有权的人确认（C16 与已登记委托）。决定人未登记，就明确写“产品决定人待核实”，由 PM 核对授权并请人补齐；产品提出具体方案后提交该决定人，核对权限并取得所需确认之前不让变更生效。接手方式的选择不等于业务批准，前台不替负责方承诺结论或时间。

- 按 C02 登记：原话、来源、收到时的阶段、初步归属。一条里含多件事就拆开。
- 判断归属，再转交：
  - 改变目标、范围、规则或验收的，交产品；
  - 用户看到的文字（提示、按钮、通知、文案表）的，交内容；
  - 交互、视觉、素材的，交设计；
  - 技术的，交研发对应的角色；
  - 影响计划、依赖或人员安排的，同时告诉 PM。
- 按 C04 发请求或唤起角色；角色的会话或子 Agent 还没有时，按 RUNTIME §4 按需拉起。通道不可用时，写好请求并告诉人"还没发出"。
- 告诉人登记位置和实际转交状态，决定权与生效条件按本节开头说明。

## 需要人决定的事

- 待决事项由各角色交给 PM，PM 按人整理成合批；你按 C01 展示：看什么、决定什么、怎么回复、卡住了谁。
- 只记录真实答复，写明原话、出处、范围；多人项目写明是谁答的（C16）。PM 用任务工具的 `configure` 登记你的身份后，你可以直接录入人工决定（X01）；否则把答复交给 PM 录入。
- 答复交回原角色继续。答复只是部分确认时，只放行对应的部分。

## 深入讨论

人要长时间讨论某一领域时，说明可以到该角色自己的会话里讨论，结论由该角色写进文件，你从文件读取，上下文不会堆在这里。人想留在这里也可以：讨论结束时把结论整理成请求交该角色写入，先按 C02 做对话核对。不强迫换地方。

## 唤起 PM 的时机

新需求或范围变化、角色上报完成或受阻、人作出决定、到了合批展示的时候。其余时候不唤起 PM，让它的上下文只装任务事件。

实质变更在接收时按 [任务完整性](../../../../matrix/orchestration/PM-INTEGRITY.md) 请 PM 登记影响分析责任与已知受影响任务；相关专业实例分别评估，计划同步后再派发，前台不代专业角色确认或修改其任务。

# 接管

何时读：首次接管项目或重建计划。调用前置与其余操作见[原入口](workflow.md)。

## 接管

- 先用 R02 的 `project` 查询类型、目标与证据责任人。用 `project_config` 把实际来源写进任务库，勿仅放在收件箱或手写进度说明里。`product_development` 沿产品研发路线；活动、研究、培训、采购等先登记类型和专业/路线缺口，本包不提供其完整路线，不强套产品基线任务。
- 收到资源约束时，分别核对任务的资源引用和 `project.resources` 的事实登记；`resource_recording_gaps` 非空就用 `project_config` 保存已有来源、独占性与实际状态，未知采购条件记待核实。随后回读 `project` 和 `continue`，报告实际写入结果及就绪顺序；已有引用或队列不能代替事实登记。
- 发现专业缺口时，先读 C01 §1 再展示其中的三个选择；选择含义以该处为准，登记仍待人的决定。

- 各源各管其事实：产品源定业务事实，设计源定具体设计，工程与检验源定技术和验证事实；历史摘要不覆盖当前有效源。
- 一句话需求：登记"澄清产品范围"等可规划的顶层任务，原话交产品角色澄清；PM 合并已知答案和重复问题后统一展示。需求已清楚就直接推进，不强制完整管理表或空泛的计划审批。
- 用户在 PM 入口展开某一领域的长讨论时，说明可以到该角色的会话里讨论、结论由角色写进文件（RUNTIME §2）；用户想留在这里也可以，PM 把结论作为请求交该角色写入，不自己改专业源。PM 在更新计划和交接前做对话核对（FEEDBACK-PROTOCOL §6）。
- 有项目前台时：按人整理待人事项、刷新视图后交前台展示；用 `configure` 登记前台身份，前台可直接录入人工决定。角色的子 Agent 按 RUNTIME §4 在它的第一项任务就绪时才创建，派发时把真实执行者写进任务。
- 已有成果的项目：从当前阶段接续，不追认未展示的成果。登记现有工作及证据；缺依据的历史项不伪造执行实例；可以只登记当前与后续任务，并说明统计边界。

## 计划与分层

- 顶层任务按 SKILL 硬性关卡 1 登记，另写范围与当前授权；派发时补真实执行者和回执。任务 ID 永久稳定，换实例不换 ID。
- 专业 owner 拆直接子项、指定执行与检验、维护日志，可再委派；各层在获得的并发额度内安排；一个任务不必对应一个 Agent。
- 部分交付用成果里程碑任务表达：依赖指向里程碑及指定版本，不复制另一份定义；生产方与接收方确认前置成立才使用，必须审阅的草稿不是就绪输入。

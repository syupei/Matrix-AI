# 试做、骨架与契约

何时读：E-2.2 对风险试做；E-2.3 搭骨架、定模块边界与接口契约、建工程基础。

## 阶段依据

阶段行用业务项目的工作状态、评审记录或本轮用户提供的事实作依据。没有项目记录时，阶段行直接写「依据：按用户描述推定；项目工作状态或技术决定记录待核实」。阶段依据栏只写项目事实及其来源。

## 风险试做

- 按 E-1 技术风险清单的顺序，只试做会改变决定、或用来证明"能否实现"的风险。例如：目标设备上的性能、包体与启动时间；联网同步与断线恢复；与既有系统或外部接口的打通；关键规则组合下的状态是否正确。
- 每项试做先写清三件事：要回答的问题；怎样算通过（数值取自 E-1 的质量场景，没有依据时标为建议值）；预计规模。
- 完成后记录实际环境、步骤、结果与限制。模拟环境、示例数据与真实设备分开写。
- 标明"用完即弃"或"保留演进"。弃用的试做代码不进入主线；保留的代码纳入工程基础的检查。
- 体验驱动程度高的项目（如游戏），与手感相关的试做做成可玩原型，由人试玩判断，不由 AI 代判好不好玩。
- 需要先锁定引擎或渲染方式时，把外观可达性也作为试做：与设计一起用候选做法做一小块画面，在目标设备上与样稿并排对照（外观目标与特征清单由设计提供，按设计[登记](../../../../matrix/professions/experience-design/profession.json)的接口要），结果进入关键选型。

## 可运行骨架

- 骨架是端到端最薄的一条真实链路：从用户入口到核心规则、数据存储，再到返回结果。它经过真实的构建与部署流程，在约定环境中运行，例如目标设备、真实平台或测试环境。骨架只覆盖核心任务的最简版本，其余功能留给 E-3。
- 用骨架验证 E-1 关键质量场景中此时能测的部分。例如在目标负载的一定比例下压测，并写明外推依据。此时测不了的，写明由 E-3 或 E-4 验证。
- 骨架带最小可观测性：结构化日志（不记个人数据与凭证）、健康检查、关键指标与告警，并按以下字段验收（C06 运维与部署 §2）：健康检查与预期响应｜隔离环境的可控错误注入｜同一事件的日志或指标｜告警接收目标与实际回执。只要求方案时列出注入和验收动作，状态写「待运行」；有可运行骨架及验证权限时执行，能查到事件且实际收到告警才填「已验证」。例如在非生产环境注入一次可识别的请求失败，按请求 ID 查日志，再核对测试告警渠道的接收时间与接收者；缺接收回执时保持待核实。
- 可玩原型或骨架能运行后，按 C13 §3 告诉人怎样试，不必等到核心评审；遇到待决的产品规则，按同一节处理。

## 模块边界与接口契约

- 模块：每个模块写职责与边界、输入与输出、运行位置（哪个进程或端），以及不得依赖的方向，例如"规则核心不依赖界面与存储"。不得依赖的方向写成自动检查。
- 跨模块、跨端或对外的接口契约逐项写明：拥有者（谁维护、谁批准修改）；运行在哪个线程或时钟上（如界面线程、逻辑帧、服务器时间）；命令与回执（发出什么，怎样知道已被接受或拒绝）；取消、超时与最终结果；版本与兼容；是否持久化，断线或重启后怎样恢复。确实不涉及的写"不涉及"，不留空。
- 契约落在代码或格式定义中，文档只做索引。
- 异常对照表：定位置与格式（T01），列内部异常或错误码、所在模块、归入的用户情境（编号与版本）与内部处理（重试、日志、告警）。界面只按情境显示，文字按键从文案表读；构建中新出现的异常先归入对照表。

## 工程基础

- 代码仓库与目录约定、依赖与版本管理、构建与部署脚本、环境配置。凭证不进入仓库。环境按 C06 运维与部署 §3 规划，中型起要有预发布环境。
- 自动检查包括：规则核心的自动测试、类型与格式检查、可自动检查的架构规则（如依赖方向），验收测试位置的保护（改动它的合入要有质量验证的检验记录），中型起默认加依赖漏洞扫描与密钥扫描（C06 安全 §2），需要时加性能基准。检查失败时阻断合入。
- 测试策略写明三件事：
  - 哪些部分测试先行。通常是规则与计算核心，用例来自产品验收标准与 E-1 场景。
  - 界面与集成怎样检验。
  - 独立检验由质量验证做：它在 E-1 交接后写验收条目，测试策略与它一起定；未接入时写明。
- 实现者不得为了通过测试而修改验收测试。

## 证据

试做、骨架或核心评审逐条列「结论｜来源（命令、环境、结果或用户提供记录）｜CORE §2 证据层级｜可证明范围｜未验证项、验证人及下一步」。单元测试、模拟器、真机和断线恢复等不同条件分行。用户提供的结果注明来源；未运行写原因和后续验证。质量门槛的放宽按 C13 §5 交人决定。

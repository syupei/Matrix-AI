# 研发流程、档位与决策权

何时读：研发角色启动或切换阶段时；PM 规划研发任务时；判断某项技术决定由谁作出时。

## 1. 四个阶段

| 阶段 | 做什么 | 出口证据 | 本包提供 |
| --- | --- | --- | --- |
| E-1 承接与建模 | 核对输入并澄清，建立逻辑工程模型；判定档位，列出技术风险 | 工程需求、逻辑模型、可度量的质量场景、技术风险清单、档位 | matrix-code-engineering-intake |
| E-2 方案与验证 | 按问题作技术决定；对主要风险试做；搭可运行骨架与工程基础；组织技术评审 | 可运行架构基线：骨架能跑，主要风险已用运行证据消除或缩小，自动检查就位，技术评审有记录 | matrix-code-engineering-solution |
| E-3 增量构建 | 按用户可见能力切成纵向增量，用任务卡组织实现；每个增量经自动检查、非实现者检验与端到端检查并入主线，并提供可试用版本 | 发布范围内的增量全部完成并通过整体回归，范围完成评审有记录 | matrix-code-engineering-build |
| E-4 发布与交接 | 冻结范围与修复、发布验收、迁移与回退演练、人的发布决定、分批发布、运维交接 | 发布版本、发布验收与决定记录、演练过的回退、交接物 | 小型、中型由 matrix-code-engineering-build 兼任；大型及以上另行配置 |

- 阶段有先后，允许局部回查：后续发现模型或方案问题，回到相关条目处理，其余成果保持有效。
- 上线后的持续运维不在本流程内；E-4 交出运维需要的交接物。
- 质量验证（matrix-quality-engineering）贯穿 E-1–4：写验收条目、做非实现者检验、范围回归与测量、发布验收与缺陷分级。
- 代码默认放在项目仓库的 `code/` 子目录（项目可以改名），内部结构由技术方案决定。`engineering/` 只放文档与证据，构建产物不入库；E-3、质量验证、E-4 分别用 `engineering/build/`、`engineering/qa/`、`engineering/release/`。一个项目拆成多个子项目的情况，本包不覆盖。

## 2. 档位

E-1 按六个维度判定档位：规模与负载；失败代价（金钱、人身安全、隐私、合规）；技术不确定性；系统复杂度（组件、技术栈、团队、既有依赖）；生命周期；体验驱动程度（是否要靠反复试玩、试用来打磨）。档位决定哪些阶段合并、开启哪些贯穿要求、人在哪里检查。某个维度偏高时，只抬高与它相关的要求。例：用户很少但涉及付款，规模按小型，付款相关代码仍须人审。

| 档位 | 形态 | 人的检查点 |
| --- | --- | --- |
| 小型 | E-1 与 E-2 合成一页技术简报：要验证什么、核心对象与规则、技术选择与理由、刻意不做什么、是否可能转为正式使用；之后做 1–3 个增量；E-4 只交交付说明与捷径清单 | 技术简报与骨架演示合并审阅一次；最终演示（即 E-3 范围完成评审），可与是否交给真实用户使用的决定合并展示；转为正式使用前升档 |
| 中型 | 完整四个阶段，可分 1–2 层 | E-1 审阅、E-2 技术评审、E-3 范围完成评审、发布决定；可试用版本随时试，不阻塞 |
| 大型及以上 | 本包只提供本文件的原则：按系统、子系统分层；超大型系统以持续变更流运行 | 按项目约定 |

- 小型档合并审阅时，同一次展示与用户答复分别记入 E-1.4 与 E-2.4 的审阅记录，不另造确认；最终演示与发布决定合并时，同样分别记入 E-3.3 与 E-4.2。
- 小型档保留"捷径清单"，列出为求快而省掉的东西；转为正式使用前逐项补齐，或由人明确接受。
- 体验驱动程度高时（如游戏、创作工具），E-2 的骨架做成可玩原型；手感与乐趣由人试玩判断，不由 AI 代判。

## 3. 贯穿要求

按档位开启：非实现者的独立检验、安全与隐私、性能与容量、运维与部署、决策与追溯记录。安全、性能、运维三项在各阶段做什么，见专项检查指引 [SECURITY](SECURITY.md)、[PERFORMANCE](PERFORMANCE.md)、[OPERATIONS](OPERATIONS.md)。产品没有提到这些事项，不等于不需要：E-1 按档位列出研发默认关注项（备份与恢复、安全基线、扩展路径、监控、升级与数据迁移），逐项处理，或写明不适用的理由。

以下两项各档位都适用：

- **可试用版本**：一有人能直接操作、且有可感知变化的版本（可玩原型、骨架、增量），就告诉相关的人怎样试：打开方式，1–3 步具体操作及应看到的结果，已知限制。试用不阻塞后续工作；试用意见按反馈处理，不等于确认或验收。
- **待决的产品规则**：在实现中显式不可用（例如提示"规则待定"），或放进标明为实验的隔离配置，不悄悄选一个默认值；在评审与交接中列出，由产品或 E-1 跟进。

## 4. 分层

同一套阶段可以在系统、子系统、功能各层重复使用。上层确定契约（接口、事件与数据格式）、预算（时延、帧时、内存、成本的分配）和必须遵循的约束；下层在约束内自主工作，并向上报告证据。

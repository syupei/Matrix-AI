# PM 统筹时的分层任务与上报

何时读：项目由 PM 统筹，或收到带父任务 ID 的工作时。没有 PM 接管时，各角色照原方式独立工作，不创建空的任务台账。专业能力、阶段、人审和成果所有权仍按各自 skill。

## 1. 分工

- PM 只规划顶层交付和跨任务依赖。收到父任务的专业角色自行拆分、登记和管理子任务；执行前列出编号、依赖与输入版本、执行者、关键交付物、检验责任和完成条件。子任务可以继续拆分。
- 任务源用 project-management-agent 的任务运行工具（`management/runtime/`）：数据库集中存放，但每项只有指定的专业负责人能更新工作内容；父任务负责人创建和关闭本层子项，PM 不逐条重写子计划。专业正文与判据留在原角色源，任务记录只引用。已有专业台账时，先在 PM 中登记入口与摘要，不另建第二套可写状态。

## 2. 向上报告

- 首次接收或拆分、计划改变、重要检查点、待核验或完成、暂停与恢复时报告：父/子任务 ID、源修订、当前与剩余量、下一动作、成果证据、影响与待人事项。先保存状态和日志，再通过实际通道报告。
- 普通内部变化归并汇总；改变跨任务接口或输入、交付承诺、范围，或需要人决定时及时报告具体影响和建议。子角色在委托内自己解决内部问题，不把所有选择上交，也不悄悄改变顶层承诺。
- 任务 ID、协作请求 ID、执行尝试和实例分开。任务事件按 event_id 去重并校验修订冲突；没有更新时先核实，不假定完成或失败，不偷偷重派。

## 3. 人的入口与完成

- PM 接管后，专业角色把问题或审阅材料交给 PM：成果链接、版本、实际检查、需确认范围、选项与建议。PM 合批展示并记录真实答复，再交回责任方处理；专业角色不另开用户问题。已有的免审委托按原范围引用，不扩大。
- 分别记录：单项产物、子任务完成、父项交付、专业检验、人的确认；角色阶段的切换以其阶段检查结果为依据（见 [STAGE-GATES](STAGE-GATES.md)）。父项关闭需满足整体条件；取消子项不能暗中删掉父项的必要验收。用户的答复不等于需求已经实现。

## 4. 各角色接入要点

- 产品：保持 S1–S7 与五类内容单一来源；首轮专业问题由产品提出、PM 统一呈现；产品不管理设计或工程的内部子项。
- 设计：保持四个人审节点及其依赖；粗结构未通过不为合批提前细化。PM 跟踪交付，不替设计作视觉判断。
- 研发承接：保持输入核对、逻辑模型、走查与交接边界；PM 出现不等于启动后续研发阶段。
- 协作运行层：继续维护真实实例、请求、回执、人工答复与恢复；可把 PM 作为主入口，但不重置已有实例、请求或数据库。

## 5. 查看与日志

项目总览按顶层统计，展开后按本层直接子项统计，不混算父子，不把数量比例当作工时或质量。每项展示编号、状态或检查点、下一任务及条件、剩余数。原始工具与测试日志留在专业证据位置，任务事件只链接；不保存模型的内部思考。生成的视图 `management/views/index.md` 只读，带修订号与时间。

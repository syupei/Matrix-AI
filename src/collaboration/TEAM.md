# 多人协作：人员、决定权与视图

何时读：项目登记了参与人、需要明确任职和决定权、PM 展示待人事项或生成个人视图时。名单只有一人也按实际权限判断；无名单的个人独立项目沿本人入口，不给受邀成员自动授予全权。

## 1. 人员名单

- 名单放在 `collaboration/people.json`，由 BOSS 或项目负责人维护。项目使用外部成员管理系统时，以它同步过来的名单为准，各角色只读。
- 每人必填 `id`（稳定的简单标识）与 `name`，按需填写：
  - `groups`：所属专业组；
  - `decides`：对哪些流程有决定权，可选 project、product、design、engineering、solution、build、release；其中 project 是项目级决定权，release 是发布决定权；
  - `scope`：具体的决定或负责范围；
  - `clarifies`：能提供哪些事实；
  - `designates`：能指定哪些人或范围；
  - `contact`：通知方式，以及在群组里的称呼；
  - `backup`：不在时的代理人。
- 顶层 `groups` 列出组的 `id` 与 `name`。

```json
{"groups": [{"id": "design", "name": "设计组"}],
 "people": [{"id": "boss", "name": "BOSS", "decides": ["project"]},
            {"id": "art-lead", "name": "美术负责人", "groups": ["design"], "decides": ["design"], "scope": "风格锚点、界面与图像素材"}]}
```

## 2. 人与事的五种关系

| 关系 | 含义 |
| --- | --- |
| 决定（decide） | 对该事项有确认权；每件待决事项都有一名直接决定人 |
| 澄清（clarify） | 提供事实或意图 |
| 指定（designate） | 分派负责人、设定委托边界、指定规范或参考 |
| 执行或试用（execute） | 由他亲自产出（任务按 [TASK-PACKET](TASK-PACKET.md) 交付），或亲自试用验收 |
| 知悉（inform） | 只需要知道结果 |

PM 任务用 `people` 字段登记这些关系，用 `derived_from` 登记派生来源，用 `awaiting` 登记正在等谁做什么（见 PM 的任务工具说明）。

## 3. 谁的确认有效

- 确认只能来自该事项的决定人，或者沿派生链往上的上游决定人；项目级决定人对全项目有效。其他人的意见记为反馈或澄清，不算确认。
- 发布决定（是否向真实用户发布、分批计划、带着已知严重问题发布）只来自项目级决定人或 `decides` 含 release 的人，不从产品、设计或研发的决定权顺延：它牵涉花钱、接受风险与运维责任。
- 冲突时上游优先。不在同一条派生链上的冲突，由两者最近的共同上游决定。
- 上游要否决下游的专业意见，先把下游的理由与影响摆给上游，再由上游决定，并记录"上游决定，与专业建议不同"。
- 决定人不明确时，请有指定权的人指定，AI 不自行认定。
- 记录确认时写明是谁（人员 id）。阶段检查与 PM 工具会核对此人是否在名单中、是否有相应的决定权；工具不认证身份。

## 4. 按人委托

每位决定人可以为自己的范围设定委托边界，边界内由 AI 决定并记录，决定人只看核心评审与抽查。技术领域使用 `engineering/技术委托边界.md`，其他领域写在该角色的依据文件中。不可委托的事项见 [CORE](CORE.md) §4。

## 5. 视图与筛选

- PM 用任务工具从任务源与名单生成以下视图，都放在 `management/views/`：
  - 全程计划表 `plan.md`；
  - 项目总入口 `project.md`；
  - 群摘要 `digest.md`；
  - 个人视图 `people/<id>.md`；
  - 专业组视图 `groups/<组>.md`。
- 一件事出现在某人的视图里，只有两种原因：他与这件事有上表中的前四种关系之一；或者这件事与他的事项有直接依赖，此时只显示上层任务。只需"知悉"的事项进入摘要。AI 角色内部的子任务不进入个人视图。
- 多人项目或中型以上项目，每个工作区在首次建立时写一份 `README.md`，只放稳定的导引：给谁看、按读者分的阅读顺序、哪些是源文件、哪些是生成物。
- 实时状态只写在各工作区的 `00-工作状态.md`，文件开头的摘要块写明：负责人、当前位置、工作情况、最新已确认成果与版本、进行中的成果、在等谁、下一步。

## 6. 群组沟通

- 只 @ 需要行动的人。同一个人同一批的事项合成一条消息，写清：做什么、看哪里、怎么回复、阻塞了谁、能不能等。
- 按里程碑或约定频率发群摘要：阶段进展、已作出的决定及决定人、受阻事项与在等谁，阻塞他人的事项放在最前。
- 不编期限。提醒间隔由项目设定；仍无回应时，请有指定权的人决定代理人。
- 群聊或私信中的意见，按 [FEEDBACK-PROTOCOL](FEEDBACK-PROTOCOL.md) 登记，不只留在聊天里。
- 通道由宿主提供（见 [RUNTIME](RUNTIME.md)）。本文件只规定发给谁、写什么。

人的任职与 Agent 团队配置按 [团队执行](TEAM-EXECUTION.md) 接续。项目/专业负责人可以委托日常组织，保留关键判断；消息送达、实际接单和决定分别记录。

# 研发流程、档位与决策权

何时读：研发角色启动或切换阶段时；PM 规划研发任务时；判断某项技术决定由谁作出时。

## 1. 四个阶段

| 阶段 | 做什么 | 出口证据 | 本包提供 |
| --- | --- | --- | --- |
| E1 承接与建模 | 核对输入并澄清，建立逻辑工程模型；判定档位，列出技术风险 | 工程需求、逻辑模型、可度量的质量场景、技术风险清单、档位 | engineering-intake-agent |
| E2 方案与验证 | 按问题作技术决定；对主要风险试做；搭可运行骨架与工程基础；组织技术评审 | 可运行架构基线：骨架能跑，主要风险已用运行证据消除或缩小，自动检查就位，技术评审有记录 | engineering-solution-agent |
| E3 增量构建 | 按用户可见能力切成纵向增量，用任务卡组织实现；每个增量经自动检查、非实现者检验与端到端检查并入主线，并提供可试用版本 | 发布范围内的增量全部完成并通过整体回归，范围完成评审有记录 | engineering-build-agent |
| E4 发布与交接 | 冻结范围与修复、发布验收、迁移与回退演练、人的发布决定、分批发布、运维交接 | 发布版本、发布验收与决定记录、演练过的回退、交接物 | 小型、中型由 engineering-build-agent 兼任；大型及以上另行配置 |

- 阶段有先后，允许局部回查：后续发现模型或方案问题，回到相关条目处理，其余成果保持有效。
- 上线后的持续运维不在本流程内；E4 交出运维需要的交接物。
- 质量验证（quality-verification-agent）贯穿 E1–E4：E1 交接后写验收条目，E3 中做非实现者检验，范围完成前做全量回归与测量，E4 中在发布候选上做发布验收并给缺陷分级。
- 代码默认放在项目仓库的 `code/` 子目录（项目可以改名），内部结构由技术方案决定并记录。`engineering/` 只放文档与证据，构建产物不入库。E3 用 `engineering/build/` 存放增量记录，质量验证用 `engineering/qa/` 存放验收条目与检验证据；E4 用 `engineering/release/` 存放发布与交接记录。一个项目拆成多个子项目的情况，本包不覆盖。

## 2. 档位

E1 按六个维度判定档位：规模与负载；失败代价（金钱、人身安全、隐私、合规）；技术不确定性；系统复杂度（组件、技术栈、团队、既有依赖）；生命周期；体验驱动程度（是否要靠反复试玩、试用来打磨）。档位决定哪些阶段合并、开启哪些贯穿要求、人在哪里检查。某个维度偏高时，只抬高与它相关的要求。例：用户很少但涉及付款，规模按小型，付款相关代码仍须人审。

| 档位 | 形态 | 人的检查点 |
| --- | --- | --- |
| 小型 | E1 与 E2 合成一页技术简报：要验证什么、核心对象与规则、技术选择与理由、刻意不做什么、是否可能转为正式使用；之后做 1–3 个增量；E4 只交交付说明与捷径清单 | 技术简报与骨架演示合并审阅一次；最终演示（即 E3 范围完成评审），可与是否交给真实用户使用的决定合并展示；转为正式使用前升档 |
| 中型 | 完整四个阶段，可分 1–2 层 | E1 审阅、E2 技术评审、E3 范围完成评审、发布决定；可试用版本随时试，不阻塞 |
| 大型及以上 | 本包只提供本文件的原则：按系统、子系统分层；超大型系统以持续变更流运行 | 按项目约定 |

- 小型档合并审阅时，同一次展示与用户答复分别记入 E1.4 与 E2.4 的审阅记录，不另造确认；最终演示与发布决定合并时，同样分别记入 E3.3 与 E4.2。
- 小型档保留"捷径清单"，列出为求快而省掉的东西；转为正式使用前逐项补齐，或由人明确接受。
- 体验驱动程度高时（如游戏、创作工具），E2 的骨架做成可玩原型；手感与乐趣由人试玩判断，不由 AI 代判。

## 3. 贯穿要求

按档位开启：非实现者的独立检验、安全与隐私、性能与容量、可运维性（需要诊断什么、怎样恢复）、决策与追溯记录。产品没有提到这些事项，不等于不需要：E1 按档位列出研发默认关注项（备份与恢复、安全基线、扩展路径、监控、升级与数据迁移），逐项处理，或写明不适用的理由。

以下两项各档位都适用：

- **可试用版本**：一有人能直接操作、且有可感知变化的版本（可玩原型、骨架、增量），就告诉相关的人怎样试：打开方式，1–3 步具体操作及应看到的结果，已知限制。试用不阻塞后续工作；试用意见按反馈处理，不等于确认或验收。
- **待决的产品规则**：在实现中显式不可用（例如提示"规则待定"），或放进标明为实验的隔离配置，不悄悄选一个默认值；在评审与交接中列出，由产品或 E1 跟进。

## 4. 分层

同一套阶段可以在系统、子系统、功能各层重复使用。上层确定契约（接口、事件与数据格式）、预算（时延、帧时、内存、成本的分配）和必须遵循的约束；下层在约束内自主工作，并向上报告证据。

## 5. 谁决定什么

| 决定 | 例子 | 谁决定 |
| --- | --- | --- |
| 产品承诺 | 删掉某个功能、改变某个操作的含义；改变用户可见结果的算法与策略（排序推荐、匹配、计价与结算、随机与公平） | 产品负责人；研发只提建议并说明代价 |
| 必须确认 | 费用与供应商、数据存放与归属、账号与支付方案、上线后的运维责任、难以回退的核心技术（客户端技术与语言、是否需要服务端及其形态、主数据存储） | 人；可在人划定的边界内委托 AI |
| 条件确认 | 扩展与可用性策略、代码组织、测试策略、主要框架与库、接口与数据格式、部署方式 | 默认委托 AI，并经独立复核；人可以展开或收回 |
| AI 自主 | 模块内实现、内部数据结构、不改变行为语义的算法、命名 | AI，留变更记录 |
| 放宽质量门槛 | 跳过测试、放宽性能预算、带已知缺陷发布 | 人；AI 不得自行关闭或放宽检查 |
| 发布 | 是否发布、发布范围与分批计划（各批对象、观察时长、继续与停止的条件）、带已知 P0/P1 发布 | 人，不可委托；AI 按已确认的计划逐批推进，触发停止条件时直接回退 |

**关键技术选型**：不论属于哪一级，对产品或实现有重大影响的决定（以后改代价大、改变用户可感知的行为、带来费用或供应商约束、涉及安全与个人数据、影响谁能维护或运行）都列为关键技术选型，由人确认：E2 中列在核心评审包第一节，人一次确认；E3 中新增的合批交人，确认前不合入。筛查问题与常见类别见 engineering-solution-agent 的技术评审指引 §2。

不可委托的四项见 [CORE](CORE.md) §4。多人项目中"人"指该范围的决定人，见 [TEAM](TEAM.md)。委托边界（包括合入前必须人审的代码类别）、核心评审与回升条件的具体做法，见 engineering-solution-agent 的技术评审指引。

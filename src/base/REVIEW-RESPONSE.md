# 4. 收到回应后

何时读：处理真实答复、判断停点或交出成果链接。调用前置与其余操作见[原入口](USER-INTERACTION.md)。

## 4. 收到回应后

| 用户的实际回应 | 你的行动 |
| --- | --- |
| 选"确认，可继续"，或上下文明确的同意 | 核对对应的请求、版本和范围；记录确认，按本角色规则保存快照；立即继续，不再问"确定吗" |
| 选"需要进行调整" | 该范围保持未确认，暂停依赖它的后续工作。用户已写明改法就直接改；没写明就用一个聚焦的问题问要改什么。改完展示新版与差异，再给两个选项 |
| 直接提出修改、只确认一部分、要求解释 | 按真实语义和范围处理；修改意见按 [FEEDBACK-PROTOCOL](FEEDBACK-PROTOCOL.md) 合批排序；解释本身不是确认 |
| 未回答、关闭控件、预选、超时 | 仍未确认 |
| "收到""已阅"或夸赞，但是否同意不清楚 | 不自动批准，只澄清真正需要的决定 |
| 存在互斥选项，用户只说"继续" | 简述选项和差异，请其选定或明确委托你决定 |
| 上一轮只是进展汇报，用户说"继续" | 直接恢复已授权工作，不追加"确认我继续"的问题，也不记为批准 |
| 已到审阅点却漏发了提示，用户说"继续" | 补发完整的审阅提示；未展示的内容不记为已批准 |
| 等待期间成果或范围已变化，或收到针对旧请求的回复 | 旧回答只适用于旧范围；核对变化，重新展示受影响部分，其他确认不清零 |
| 新对话里说"继续" | 读工作状态和实际成果；只有存在真实未决的审阅请求时，才重新展示入口 |

在原有的审阅或确认记录中关联：请求、成果版本或快照、范围、展示依据、实际答复、处理结果；审阅节点的请求与回应同时按 [STAGE-GATES](STAGE-GATES.md) 存成记录文件，供阶段切换检查。区分"待展示""已展示待回应""已解决或已替代"；写进文件只是准备好了请求，不等于已经展示。不编造消息编号。

## 5. 能否结束本轮

| 实际情况 | 现在做什么 | 最终回复 |
| --- | --- | --- |
| 还有已授权、输入足够、不依赖新确认的工作 | 继续做到下一个真实审阅点或约定范围完成 | 暂不发最终回复 |
| 到达审阅点，或存在必须由人明确的缺口 | 先完成可独立处理的部分，再交出成果与问题 | 按[第 2 节](REVIEW-PREPARE.md#2-审阅提示写什么)写审阅提示 |
| 约定范围已完成，或用户要求暂停 | 保存成果和实际状态 | 说明完成范围或暂停原因，写出下一步和由谁触发；可以写"你无需操作"，但不省掉下一步 |
| 在等外部结果（其他 Agent、专家、工具） | 先做其他独立工作；核实请求是否真的发出、谁返回、怎样恢复 | 有确证的自动恢复机制才可说"结果到了会继续"；否则说明需要谁、做什么来恢复 |
| 工具失败或确有执行限制 | 保存断点、已完成和未完成的范围及失败证据；可修复的小故障先修复 | 标明受阻与恢复所需的动作；如需用户发消息才能恢复，直接说明，并说明这条消息不代表批准草稿 |

阶段名称、写完一部分文件、已宣布下一步、想展示进度，都不是停下的理由；也不要用"执行限制""上下文不足"之类的说法为普通停顿找理由。状态文件里不能在停下后保留"正在处理、无需操作"之类的过时描述。

## 6. 成果链接

- 先保存并回读成果，再给链接；核对文件存在、版本和所指章节。
- 用宿主可点击的格式，通常是指向当前项目内文件的 Markdown 链接；路径含空格等特殊字符时按宿主要求处理。链接文字写人能看懂的内容，例如"审阅目标与首期范围"。
- 宿主支持行号时才给已核实的行号；不编造行号，不链接到模板、旧快照或其他项目来冒充当前成果。
- 链接不可用时直接说明，并把需要确认的实质内容展示在对话里。
- 本地表单：给出项目中真实表单的链接，说明用浏览器打开、导出后怎样交回；本地文件不会自动把答案发回对话，表单工具调用成功也不代表用户已提交。

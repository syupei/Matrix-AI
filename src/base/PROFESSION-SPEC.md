# 专业规范

何时读：创建或修改一个专业时，按"专业创建"技能的步骤使用。实例运行时不需要读。

## 1. 每个专业要写清的

1. **身份**：标识、名称、类别（调度、定义、制作、保障与审查）、版本、需要的技能包版本。专业标识就是岗位：实例配置、派活、缺口与收发都只认它。本包自带的技能命名为 `matrix-<专业标识>`，几个技能组成一个专业时加阶段，例如 `matrix-code-engineering-build`；换成项目自己的 Agent 时，名字不限，在实例配置里写明承担哪个专业标识；有阶段的专业另有缩写，阶段编号写成 `缩写-序号`，例如质量工程的 `Q-1`。
2. **范围**：
   - 能处理与不处理的问题；
   - 与哪些专业交界；
   - 参与的触发条件，供项目启动时由人决定、由前台推荐。
3. **负责的成果**：每类成果的正式来源；别处只放带版本的摘录。另写本专业的复用单位（C00 §3"先归类"），例如用户情境、文案键、页面模板、函数与组件。
4. **评判标准**：什么算好，引用的能力标准或行业标准。
5. **阶段与人审点**：写成结构化数据，阶段检查从登记读取。
6. **决定权**：
   - 自己能定什么；
   - 交出去什么：交人，或交其他专业；
   - 哪些结论有约束力。
7. **接口**：
   - 需要谁提供什么、交给谁什么，带版本；
   - 共同维护的契约，写明各自负责哪一部分、改动怎样通知对方；
   - 输入：每个阶段需要上游的哪个阶段、到什么状态。条目输入默认按上游条目的风险：F0–F1 等确认；F2 可以用草稿先开工，确认后复核；F3–F5 用草稿即可。可以要求得更严，不能更松。
8. **工具与做法**：需要的能力，不写具体宿主或模型。
9. **实例需要的模型能力**：例如能看图。模型适用表据此判断某个模型能否派生本专业的实例。
10. **职级表**（C21）：
    - 使用的 T 范围，以及 master 的最低职级；
    - 每一级写能做、能判断、不能做。
11. **风险与缺陷对照**（C22）：F、Q 每一级在本专业的例子，按共用定义，不改含义。
12. **检验与汇报**：
    - 由谁检验，独立性要求；
    - 向 PM 汇报什么，包括需要主动告知人的事项。
13. **评测**：
    - 本专业的情境，至少覆盖每个人审点和最常见的风险；
    - 另外要通过所有专业共用的底座情境。

新专业接过现有专业的部分职责时，写明现有专业要改什么（接管）。

## 2. 登记文件

- **位置**：
  - 每个专业一个文件夹 `matrix/professions/<标识>/`：登记 `profession.json`，职级表与对照 `levels.md`，只属于这个专业的规则也放在这里；
  - 技能平放在宿主的技能目录，登记的 `skills` 列出它们；
  - 由几个技能组成的专业，只有一份登记。
- **字段**：按第 1 节逐项对应，格式版本写在 `schema` 字段，供其他平台读取。
- **总入口**：[总入口](MATRIX.md)的专业目录由各专业的登记生成（专业创建技能的生成脚本），不手工维护。

## 3. 内容规范

- **与宿主和模型无关**：只描述需要的能力（例如"宿主提供的选项式提问工具"），不写特定宿主或模型的工具名。
- **可以公开下载**：不含本机路径、项目名、制作过程、版本沿革、决定编号或真实品牌示例；只描述当前规则。
- **按需加载**：
  - 启动时只读入口、本角色的指引索引、共用规则索引和共同底线；
  - 其余文件写明"何时读"；
  - 能力标准按需逐份读取。
- **字数预算**（字符）：
  - 安装写入的入口块 ≤ 1,200；
  - SKILL.md ≤ 3,500；
  - 角色指引索引 ≤ 1,500；
  - 共用规则索引 ≤ 2,500；
  - 单个参考文件一般 ≤ 3,000；
  - 超出要说明理由。
- **一条规则写一处**：引用而不复述。
- **每条规则对应一个真实问题**：写明它要防止的失败、怎样判断是否生效；能做成模板、脚本或检查点的，不靠措辞。

## 4. 接入前的检查

- 运行专业创建技能的登记检查脚本：
  - 登记完整；
  - 职级在 T1–T9 之内，每级三项都有；
  - 对照覆盖 F0–F5 与 Q0–Q5；
  - 阶段编号的写法与缩写不重复；
  - 输入引用的专业与阶段存在，条目输入不比默认更松；制作类与定义类专业写了复用单位；
  - 链接有效；
  - 字数在预算内。
- 通过底座情境与本专业情境的评测。

# 输入核对与澄清

何时读：E1.1 接收与核对；E1.2 发现缺口需要回查时。

## 接收（E1.1）

- 从产品定义/交付索引读实际的 MODEL、BEHAVIOR、INTERACTION、STYLE、ACCEPTANCE 及相关确认、变更、问题与反馈，再从设计依据/交付索引读规格和实际设计源。文件名不同就沿用项目位置。
- 核对版本、有效确认、实际内容与可访问性。路径未知或关键输入缺失时，先在授权项目内查找，再请求实际位置或资料，不让人重述已有资料。材料齐备就进入建模，不另要"确认接收"。
- 产品采用结构化交付时按 [STRUCTURED-HANDOFF](../../../../collaboration/STRUCTURED-HANDOFF.md) 核对快照与当前范围，区分"待后续验证"与"当前阻断"；不为消除报警改动产品正文或快照。
- 设计只核验影响工程判断的实际源和行为，不重做设计审查。打不开画布、文件或预览时记录限制与可继续范围，不凭标题或截图推断完整交互。
- 现有技术环境只读检查；空项目不建应用骨架，现有原型不自动成为生产选型，用户锁定的技术是输入约束。

## 按适用性核对

每项记为：已明确（附依据）/ 待澄清 / 授权内工程判断 / 下游方案或验证依赖 / 不适用（附理由）。未检查不能标不适用。

- 意图与交付范围（MODEL、确认与交付说明）：目标、用户角色、任务、端与语言、首期边界、必须保持的承诺。
- 业务语义（MODEL、BEHAVIOR、AC）：对象、属性口径、关系、权限、合法状态、操作结果与关联后果。
- 行为与具体体验（INTERACTION、设计规格与实际源）：前提、输入、反馈、结果，异常/中断/重复/恢复，界面状态与业务状态的对应。
- 系统边界与外部依赖（产品流程、外部责任方与接口资料）：事实与数据的负责方、人工环节、外部输入/返回及失败责任、接口资料可得性。
- 数据生命周期（产品规则、现有数据、来源专家）：身份与唯一性、来源、保留/删除、历史兼容、导入导出、访问与敏感边界；没有需求不新增功能。
- 工程质量条件（既有要求、使用证据、责任方、工程分析）：哪个任务在何种负载、网络、端、数据条件下的预期、可接受边界和验证方式。
- 现有工程与现实约束（项目资料、实际配置与代码、环境责任方）：可复用系统、锁定技术、运行环境、接口、依赖版本、许可、资源与成本；不输出凭证。
- 验收与证据（ACCEPTANCE、设计验证、实际报告）：AC、覆盖、模拟范围、未实测项、条件与来源版本。

## 质量要求具体化

按实际风险选择性能/容量、可靠性/恢复、安全/隐私、兼容、可测试、可维护、可运维。重要项写清对象或操作、条件、要求或边界、来源与性质、验收方式、待决影响；"高性能""易运维"要落到场景。例：只有"响应要快"时，提出测量方法和目标建议，不填毫秒值作硬约束；负载未知时说明它影响哪些技术决定、怎样取得依据，不默认互联网规模。

发布后的持续监测不在 E1 范围；架构需要的诊断、恢复、健康检查在此写明目的与验收依赖，由 E2 设计、E3 实现，小项目不强制全套。

## 缺口怎样处理

| 缺口性质 | 行动 |
| --- | --- |
| 原文已有，自己没找到 | 读对应条目直接转译，不向人提问 |
| 产品事实、规则或结果承诺缺失或冲突 | 向产品发请求，附版本、已查依据、影响与建议 |
| 具体交互、文案、布局缺口 | 向设计请求；牵涉业务含义时关联产品问题，不让两方各编一套 |
| 外部系统、环境或领域事实未知 | 找实际资料和知情方，不以 Agent 之间的共识代替，不反复向产品索取 |
| 依据内的工程表示或可逆推导 | 自行完成并写明理由 |
| 技术路线或机制未定 | 有目标、约束和判据时交 E2；缺业务期望时不假称自由度 |
| 只有原型或实现能验证 | 记为验证依赖；决定当前模型或关键方案时前置验证或限定范围 |

- 缺口记录：唯一 ID、来源、阻断范围、责任方或"未指定"、所需信息或证据、解除条件、须在哪个决定前解决（不设无依据的日期）。同源问题聚合但各保留含义；已有共用问题或反馈直接引用。
- 只问影响当前决定的问题，按来源聚合；不以"请确认需求是否完整"让人代做检查。核心规则缺口不以"待测试"掩盖，纯视觉细节或局部实现选择不阻断全部业务建模。

## 文案输入

按 [COPY-QUALITY](../../../../collaboration/COPY-QUALITY.md) 承接成稿版本、表达约束和状态/变量映射；原稿或工具返回将被直接展示时作为设计缺口回传。工程条件中的"与源文一致"指业务语义保真，不锁死原句。

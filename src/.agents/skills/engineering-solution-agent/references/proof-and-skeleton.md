# 试做、骨架与契约

何时读：E2.2 对风险试做；E2.3 搭骨架、定模块边界与接口契约、建工程基础。

## 风险试做

- 按 E1 技术风险清单的顺序，只试做会改变决定、或用来证明"能否实现"的风险。例如：目标设备上的性能、包体与启动时间；联网同步与断线恢复；与既有系统或外部接口的打通；关键规则组合下的状态是否正确。
- 每项试做先写清三件事：要回答的问题；怎样算通过（数值取自 E1 的质量场景，没有依据时标为建议值）；预计规模。
- 完成后记录实际环境、步骤、结果与限制。模拟环境、示例数据与真实设备分开写。
- 标明"用完即弃"或"保留演进"。弃用的试做代码不进入主线；保留的代码纳入工程基础的检查。
- 体验驱动程度高的项目（如游戏），与手感相关的试做做成可玩原型，由人试玩判断，不由 AI 代判好不好玩。

## 可运行骨架

- 骨架是端到端最薄的一条真实链路：从用户入口到核心规则、数据存储，再到返回结果。它经过真实的构建与部署流程，在约定环境中运行，例如目标设备、真实平台或测试环境。骨架只覆盖核心任务的最简版本，其余功能留给 E3。
- 用骨架验证 E1 关键质量场景中此时能测的部分。例如在目标负载的一定比例下压测，并写明外推依据。此时测不了的，写明由 E3 或 E4 验证。
- 骨架带最小可观测性：结构化日志（不记个人数据与凭证）、健康检查、关键指标与告警，并制造一次错误实际验证能查到、能收到（C06 运维与部署 §2）。
- 可玩原型或骨架能运行后，按 C02 §3 告诉人怎样试，不必等到核心评审；遇到待决的产品规则，按同一节处理。

## 模块边界与接口契约

- 模块：每个模块写职责与边界、输入与输出、运行位置（哪个进程或端），以及不得依赖的方向，例如"规则核心不依赖界面与存储"。不得依赖的方向写成自动检查。
- 跨模块、跨端或对外的接口契约逐项写明：拥有者（谁维护、谁批准修改）；运行在哪个线程或时钟上（如界面线程、逻辑帧、服务器时间）；命令与回执（发出什么，怎样知道已被接受或拒绝）；取消、超时与最终结果；版本与兼容；是否持久化，断线或重启后怎样恢复。确实不涉及的写"不涉及"，不留空。
- 契约落在代码或格式定义中，文档只做索引。

## 工程基础

- 代码仓库与目录约定、依赖与版本管理、构建与部署脚本、环境配置。凭证不进入仓库。环境按 C06 运维与部署 §3 规划，中型起要有预发布环境。
- 自动检查包括：规则核心的自动测试、类型与格式检查、可自动检查的架构规则（如依赖方向），验收测试位置的保护（改动它的合入要有质量验证的检验记录），中型起默认加依赖漏洞扫描与密钥扫描（C06 安全 §2），需要时加性能基准。检查失败时阻断合入。
- 测试策略写明三件事：
  - 哪些部分测试先行。通常是规则与计算核心，用例来自产品验收标准与 E1 场景。
  - 界面与集成怎样检验。
  - 独立检验由质量验证做：它在 E1 交接后写验收条目，测试策略与它一起定；未接入时写明。
- 实现者不得为了通过测试而修改验收测试。

## 证据

试做与骨架的结论都引用实际运行记录：命令、环境、结果，并按 CORE §2 写明证据层级与不能证明的部分。没有运行的写"未运行"并说明原因。任何质量门槛的放宽，按 C02 §5 交人决定。

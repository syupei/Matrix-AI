# 决定与约束

何时读：E2.1 收集约束；E2.2 作技术决定；回查需要改变决定时。

## 收集约束（E2.1）

- 读 E1 交接：工程需求与模型的版本、档位、技术风险清单，以及"必须保持"和"交由 E2 决定"的事项。产品的运行形态（渠道、联网与互动方式、账号与数据、付费、规模、合规）缺失时，经 E1 回问产品，用业务语言提问，不自行假定。
- 只读检查既有环境：已有代码、系统、接口、账号与供应商、团队技术规范。不输出凭证。
- 按 R03 取得技术委托边界。

## 按问题作决定（E2.2）

1. 先写要解决的问题，再列选项。混在一起的问题先拆开。
   - "测试先行还是领域驱动"：前者管怎样证明代码写对了，后者管业务概念怎样组织进代码，两者不是二选一。
   - "用哪种数据存储"：先按数据种类分开，例如需持久可靠的交易与账号、可以过期的会话与进行中状态、可以重建的统计，再分别决定。
2. 每个决定写清：问题、选项（"必须确认"类至少两个可行选项）、推荐、依据（约束、试做或实测数据）、后果（大致成本、由谁维护、以后改变的代价、对体验的影响）、验证与推翻条件（靠哪项试做、骨架运行或自动检查证明它可行；出现什么结果就重新决定）、级别（必须确认、条件确认或 AI 自主，见 C02 §5）、是否为关键技术选型（命中 R03 §2 的哪几问）、状态（已确认、按边界委托、委托复核、待定）。
3. 依据不足的决定交给试做（R02）取得证据，不凭印象定。
4. 决定之间有依赖时写明顺序。例如客户端技术取决于发布渠道与包体要求；服务端形态取决于联网与互动方式和规模。
5. 编程风格可以分区：规则核心、界面表现、数据访问各按自己的问题选写法，不必全项目统一。

## 不确定时

- 保留以后扩展的余地成本很低时，默认保留，但不提前建设。例如回合制服务不在进程内保存进行中的状态，以后加实例即可扩容，但暂不引入复杂的编排平台。
- 保留余地成本很高时，列为"必须确认"，写明后果交人决定。
- 两种情况都把所依据的假设和重新评估的时机写进该决定的验证与推翻条件，例如"高峰同时在线超过某个数值时启用多实例"。

## 模型落成可执行形式

E1 的逻辑模型在 E2、E3 中逐步落成数据结构定义、接口契约（要素见 R02）与验收测试。文档改为索引与解释，指向这些可执行形式，不维护第二份平行的模型。映射有变化时，请 E1 同步引用。

## 反馈与回查

- 产品承诺、业务规则或逻辑模型的问题：回到产品或 E1，附影响与建议，不在方案中改变行为。
- 已确认的决定需要改变：按回升条件（R03 §3）交人，只复核受影响的决定与约束。

# 专业 Agent 协作编排

版本：0.9

把跨角色的具体问题交给真实的责任角色实例处理并接续请求方；不代替专业判断，不做项目排期，不改变各角色的能力标准与授权。

## 启动

1. 读 [CORE](../../../collaboration/CORE.md)、本目录 [GUIDANCE-INDEX](GUIDANCE-INDEX.md) 与 C02。
2. 判断身份：发起请求 / 协调派发 / 责任角色处理请求 / 恢复待决请求。
3. 用 `status` 恢复已登记角色、在途请求与人工问题；未初始化时用 `init`（R01）登记真实对人主任务与授权（模板不算授权）。

## 工作流

| 阶段 | 做什么 | 产出 | 人审 | 读 |
| --- | --- | --- | --- | --- |
| 1 发起 | 请求方先查已有依据；本轮确需其他角色时建一个具体请求：条目与版本、问题与影响、期望返回、可改范围与授权；之后继续无依赖工作 | `request` | — | R01 C03 |
| 2 路由 | 协调方复用或按需创建真实实例，只读就绪握手后登记；领取后发送完整请求包 | `register` `claim` `receipt` | — | R01 R02 |
| 3 处理 | 责任角色能依现有事实解释或在委托内决定就答复并附依据；否则返回需要人（问题、原因、范围、选项、建议）；缺资料或工具先诊断 | `respond` | — | R01 |
| 4 回收 | 协调方有界等待并在本轮继续，核对 token 与版本；请求方采用后关闭 | `accept` | — | R01 R02 |
| 5 需要人 | 合并同源问题，在对人入口展示该版本问题；真实回复后唤醒原责任角色给出正式结论，再由请求方采用 | `presented` `human_answer` | 是 | C01 R01 |

## 硬性关卡

1. 有具体跨角色问题就实际派发和接续：不只写请求文件就停，不让一个执行者扮演多个角色冒充共识。
2. 没有宿主真实返回的句柄或发送结果，不登记实例、不记 sent；发送结果不明记 uncertain，核对后再定，不超时重发。
3. 同一业务源同时只有一个写者。cancel 不会停止执行者；取得停止或完成证据并 `settle_cancel` 后才换写者或路由。
4. 回复（answered）不等于请求方采用或用户批准；请求方核对当前版本并 `accept` 后才关闭。
5. 真实展示后才记 `presented`，收到用户真实回复才记 `human_answer`；答复交原责任角色处理，不直接记为已实现。
6. 源已变化、已取消或被替代的结果不自动采用；按新版本建新请求并注明替代关系。
7. 用户新补充先按 [FEEDBACK-PROTOCOL](../../../collaboration/FEEDBACK-PROTOCOL.md) 合批并由责任方排序，不按到达顺序派发互相覆盖的修改。

## 职责边界

- 常规澄清自主进行；产品范围、用户承诺、重要取舍与各角色阶段审阅按既有授权处理。协作授权不批准研发候选，不启动后续研发阶段、整套设计、部署或持续运营。
- 责任角色只处理指定请求：不因读取某 skill 就重启该角色访谈，不读无关会话；默认只读，请求含 `write_allowed` 且已有授权覆盖时才改本角色源。不直接问人，不让用户到别处回复；需要其他角色时提关联请求，由协调方路由。
- skill、角色实例、消息工具是三件事：加载 skill 不等于与该角色实例通信，共用能力 skill 不产生新实例。保持各实例的模型设置；用户未要求时不创建用户侧新任务；不装守护进程或定时任务。
- 运行状态只记在账本，专业内容以各角色文件为准；账本不锁业务文件，角色标签与人工记录是协作性校验，不是身份认证。
- 文案、结构化交付、定位变更请求按 C04 携带所需字段，由有效源维护方合并；回复不等于质量通过或已落实。

## 完成的含义

请求 closed：请求方已核对当前版本并记录采用结果；涉及人决定的，原责任角色已按真实答复给出正式结论。

## PM 统筹时

项目由 PM 统筹或收到带父任务 ID 的工作时，按 [PM-REPORTING](../../../collaboration/PM-REPORTING.md) 在委托内自管子计划与日志，执行前登记子项并上报父任务关联。需要人的问题交 PM 合批展示，真实答复后由本角色继续；PM 未接管时照常工作。PM 作为对人主任务入口时，沿用已有实例、请求与账本，任务事件引用请求 ID，不另建队列。

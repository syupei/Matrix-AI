# P1-5 状态体系设计能力

> 《产品领域专家能力要求模型》P1 产品逻辑 V1.1 原文，按章节拆分，正文未改写。

### 6. 状态体系设计能力

能力定义

定义产品对象或关系在生命周期中可以处于哪些产品状态，每一状态代表什么事实，状态之间如何转换，以及转换的触发条件、结果、可逆性、终止方式和历史保留原则。

这里的状态是用户与产品能够共同理解、据此判断和行动的产品事实，不是代码枚举、服务运行状态或页面的临时显示状态。

核心问题

状态属于哪个对象或关系，代表什么已经成立的事实？

不同状态是互斥、并行、包含还是派生关系？

哪些转换合法，由什么动作或事件触发，转换后改变了什么？

哪些变化可撤销、回退、重开或终止，哪些历史事实必须保留？

关注重点

状态归属与状态语义；

对象生命周期及状态集合的完整性；

转换条件、方向、结果、可逆性和终止；

并行状态、派生状态和聚合状态的合理性；

修改、撤销、失效、重开和历史版本；

同一事实在不同入口、角色和终端中的一致性。

为什么重要

状态体系使变化成为可理解、可判断和可推导的产品事实。状态归属含混时，产品会用一个“总状态”覆盖多个同时成立的事实，或用页面文案临时描述进展，最终导致历史丢失、规则冲突和跨入口矛盾。

常见错误

不说明状态属于会议、邀请、参与关系还是响应；

用单一总状态覆盖多个对象的并行事实；

只设计正向转换，不考虑撤销、回退、过期、重开和终止；

将“已修改”长期作为状态，却不定义修改影响了什么事实；

直接暴露技术处理阶段，用户无法据此理解和行动。

简洁案例

会议可处于草稿、已安排、已取消、已结束；邀请可处于未发送、已发送、发送失败、已撤回；参与者响应可处于待响应、接受、暂定、拒绝、需重新确认。会议时间修改是一次事件；当它触及关键承诺时，保留原响应历史，同时把当前响应转为“需重新确认”。

与相邻能力边界

“对象关系设计能力”确定状态依附的对象或关系；本能力定义状态事实与合法变化；“产品规则体系设计能力”定义谁能在什么条件下触发转换。一级能力“过程与状态”关注用户如何经历等待、进展、中断和恢复，不负责定义产品状态事实。

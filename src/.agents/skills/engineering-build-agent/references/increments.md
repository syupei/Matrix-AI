# 增量与任务卡

何时读：E3.1 接收与规划；每个增量开始前。

## 接收（E3.1）

- 先核对技术方案的 E2.4 核心评审已确认：读 `engineering/solution/` 中的评审记录与交接（项目另有位置时沿用）。没有确认时说明缺口，可以先起草增量计划，但不开始实现；阶段检查会在进入 E3.2 时核对。
- 读 E2 交接：必须遵循的约束（已确认与已委托的决定）、模块与契约、骨架与工程基础的入口、测试策略、未消除的风险与验证责任。再读产品验收标准（AC）、E1 场景与设计交付中属于发布范围的部分。
- 输入缺失或互相矛盾时，按 C04 回到维护方，只暂停受影响的增量。

## 切增量

- 按用户可见的能力切：每个增量从入口、界面、规则到数据纵向打通，完成后可以演示。不按"先做全部数据，再做全部接口"横切。
- 排序：E2 留下的未消除风险先做，其次是能解除别人阻塞的，再按价值。
- 一个增量控制在几张任务卡之内，做不完就再切。
- 逐个标明：
  - 引用的 AC 或场景；
  - 是否涉及界面、需要设计走查；
  - 是否需要人的试用，即产品或设计要求由人判断的体验，例如手感；
  - 是否含委托边界中必须人审的代码类别（X01 §1）。
- 不依赖界面的逻辑可以在设计定稿前开始，界面部分以设计走查通过为完成前置；输入取决于设计结论的部分，等结论再做。
- 增量计划不需要人批准。它进入项目视图，人可以随时调整，调整记入计划的变更记录。进度按维度登记（T01），不用总百分比。
- 一并列出发布前只能由人办、耗时较长的事项（R04），经 PM 合批或按 C01 提前提出，不等到 E4。

## 任务卡

任务卡把"做什么、按什么做、怎样算完成"写在一处，编码子任务只读它和它引用的源。

| 字段 | 内容 |
| --- | --- |
| 编号与所属增量 | 如 INC-2/T-3 |
| 目标 | 完成后用户能做到什么 |
| 引用（必填） | 功能或对象（产品 ID）、决定（TD-编号）、验收（AC 或场景编号）；涉及界面时加设计规格 |
| 输入与版本 | 上游成果及版本 |
| 约束 | 模块边界、接口契约、不得依赖的方向 |
| 完成证据 | 对应的验收条目（TA 编号）、到哪一层（CORE §2）、端到端检查怎样走 |
| 检验者 | 质量验证；未接入时为另起的检验子任务，不是实现者 |

- 能关闭任务的只有"某条验收在某一层通过"，并附运行记录。"已接入某 SDK""有 N 条数据""基本完成""本地能跑"都不能关闭任务。
- PM 统筹时，增量登记为 E3 顶层任务下的子任务：引用与输入写进 inputs，完成证据写进 criteria，设计走查与人的试用登记为完成前置（`completion_requires`），含必须人审的代码时设 `human_required`。不另存一份任务卡。
- 大型档按子系统分层，每层用同一套步骤；维护系统地图与模块说明，编码子任务按需读取，不一次装入全部代码。

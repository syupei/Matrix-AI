# 发布准备与发布决定

何时读：E4.1 发布准备；E4.2 发布决定；E3.1 列出发布前只能由人办的事项时。

## 开始与范围

- 开始条件：范围完成评审（E3.3）已确认，且人决定进入发布准备，两者都有记录。离开 E4.1 时，阶段检查会重新核对 E3.3 的确认仍然有效（C05）。
- 冻结范围：只接受分级缺陷的修复与发布必需的改动（配置、开关、迁移脚本），新功能留到下一次发布。修复照常走增量循环（R02），由质量验证复验。
- 面向用户的发布说明与商店文案由产品提供，按文案审读处理；E3.3 之后有改动的界面，按 C04 请设计走查受影响的部分。

## 只能由人办的事项

E3.1 规划增量时一并列出，经 PM 合批或按 C01 提前提出，不等到 E4：

- 应用商店或平台账号、资质与备案；
- 隐私政策等合规材料；
- 生产环境的付费服务（费用与签约，CORE §4）；
- 上线后的运维负责人（C02 §5 必须确认）。

E4.1 开始时核对状态，没办好的写进决定包。小型档只列实际需要的。

## 发布候选

- 用 E2 建立的构建与部署流程产出，在候选清单（T02）中记录：版本、提交与标签、构建标识、包含的增量、E3.3 之后的改动。
- 请质量验证做发布验收：附候选清单、部署好的交付形态（打包后的应用、预发布环境中的服务）。它全量回归，按约定测性能、安全与兼容，并按 P0–P2 分级（X02）。修复后由它复验，候选清单随之更新。

## 演练

- 回退：在发布前的环境中先部署新版本，再回退到当前线上的版本，核对功能与数据。没有实际做过，就写"回退未演练"并在决定包中单列。
- 数据迁移：在与生产相似的数据副本上演练，不用真实个人数据；记录耗时与核对结果。需要改数据结构时，优先拆成兼容的两步：先加新结构，等线上不再有使用原结构的版本后再删原结构，这样回退后的版本仍能读写数据。不可回退的迁移按 X01 §3 交人。
- 客户端：已安装的应用无法回滚。新功能放在服务端开关后面，必要时强制更新；开关与强制更新要在发布前验证过。
- 每项演练写环境、步骤、结果与证据层级（CORE §2）。

## 分批计划

- 每批写：对象或比例、观察多久、看哪些指标、继续的条件、停止的条件与回退方式。阈值取自质量场景与服务目标，没有依据的标为建议值。
- 人在发布决定中确认整个计划后，按计划推进，只在触发停止条件或需要偏离计划时找人。人也可以在决定中改为逐批确认。
- 只发给内部或部分用户时，同样写计划。

## 发布决定包（一页）

1. 发布什么：版本与构建标识、范围（对照 E3.3）、E3.3 之后的改动。
2. 怎样发布：环境、分批计划、回退方式与演练记录；客户端的开关与强制更新。
3. 证据与边界：发布验收在交付形态与真实环境中到了哪一层；性能、安全、兼容的测量；没达到的层级由谁在何时验证。
4. 已知问题：按 P0–P2 列出，P0/P1 单列；任何降级写明原因与提出者。
5. 需要人决定或已由人提供的：费用与账号、合规材料、运维负责人；有 P0/P1 时逐条写影响、可选做法（推迟、关闭入口、限定范围）与建议。
6. 交接包清单与状态（R05）。

## 请人决定（E4.2）

- 按 C01 展示，请人决定：发布、不发布，或只发给内部或部分用户。按 C05 记录，决定绑定决定包与候选清单的摘要。决定之后候选有变化，原决定失效，就变化部分重新请人决定，可以从简。
- 发布决定只能由人作出（CORE §4）。多人项目中，只有项目级决定人或被指定的发布决定人能决定（TEAM §3），其他人的意见记为反馈。
- 带着 P0/P1 发布是接受已知的严重风险：只认针对具体条目、具体版本的决定，并记录接受范围与缓解办法。听到笼统的"先发吧"，先把这些摆给决定人，再记录。
- 小型档：交付说明与捷径清单按 T02 的小型档部分写；是否交给真实用户使用，可以与最终演示合并展示，E3.3 与 E4.2 两条记录分开。转为正式使用前先升档（C02 §2）：捷径清单逐项补齐或由人明确接受，再按中型档发布。

# 实现、检验与上报

何时读：E3.2 每个增量的实现、检验与合入；需要上报时。

## 每个增量的顺序

任务卡 → 实现 → 自动检查 → 交叉审查 → 非实现者检验 → 端到端检查 → 并入主线 → 可试用通知。前一步不通过，不进入下一步。

## 实现

- 宿主能派发编码子任务时，按任务卡派发，只给任务卡和它引用的源；收回代码与运行记录后由你审查；外部执行者的回交按[外发任务包](../../../../collaboration/TASK-PACKET.md) §3 核对，只算自检。不能派发时自己实现，检验仍由非实现者做。
- 小步改动。每次合入对应任务卡与测试，并写变更记录，人随时能查到最近改了什么。
- 模块内的实现（不改变行为语义的算法、内部结构、命名、重构）自主决定。要引入新的存储、第三方服务或组件，或改变行为语义的算法（如顺序、一致性、重试）时，先按 X01 §2 筛查：命中的是关键技术选型，确认前不合入；普通工具库记入依赖清单。
- 设计规格没覆盖的界面状态，先用设计系统中最接近的已有组件或样式顶上，不另创新样式，标为临时界面并列入走查请求。产品规则的缺口不适用这一条，按 C02 §3 处理。

## 检查与审查

- 自动检查（E2 建立）在每次合入前运行，失败就阻断合入。测试失败时不跳过、不改验收测试、不放宽门槛；修不好就上报，放宽质量门槛由人决定。
- 每个改动由非作者做 AI 交叉审查，重点看：是否符合任务卡与契约；依赖方向；新引入的依赖、存储或算法是否命中关键技术选型；日志与报错中是否带出个人数据或凭证；假完成的迹象，如用桩代替真实行为、吞掉错误、跳过或删改测试、写死的数据。
- 委托边界中列为必须人审的代码类别（X01 §1），合入前交人审：给出改动摘要、风险、测试与运行记录，合批展示。其余代码按边界中的比例由人事后抽查。

## 非实现者检验

- 由质量验证（quality-verification-agent）检验：发检验请求，附任务卡、可试用版本与对应的验收条目编号。质量验证未接入时，另起一个与实现者分开的检验子任务（全新上下文），按任务卡逐条检验验收，写明证据层级，记为"由 AI 检验"；宿主不支持子任务时，如实写"未做独立检验"。
- 检验者不修改被检验的代码与验收测试；发现问题退回实现。

## 端到端与合入

- 每个增量的出口：在主线上从用户入口走到结果，并通过整体的自动检查。各模块分别通过不算。
- 涉及界面的增量，按 C04 请设计走查，附可试用版本、对应的设计规格、已知限制与临时界面清单；设计回复一致、偏差清单或需要产品决定，实现偏差改完后再请走查。体验驱动的项目，核心场景第一次实现时由设计决定人亲自看一次，并入该增量的人的试用。设计未接入时如实记录。
- 增量完成后按 C02 §3 发可试用通知；试用意见按 C03 处理，不等于确认。需要人判断体验的增量，以人的判断为完成前置。

## 上报

| 情况 | 去向 |
| --- | --- |
| 超出委托边界、命中回升条件、需要改变已确认的决定 | 按 X01 §3 交人；E2 只复核受影响的条目 |
| 跨模块契约变更 | 兼容的改动由你决定，经交叉审查并通知相关模块与质量验证；不兼容的改动按上一行处理 |
| 新增的选型是关键技术选型（X01 §2） | 按 X01 §3 合批交人确认，确认前不合入 |
| 需要放宽质量门槛、跳过测试、带已知缺陷继续 | 交人决定 |
| 产品规则缺失或冲突 | 按 C02 §3 处理待决规则，回到产品 |
| 实现与设计不一致，且无法在设计范围内解决 | 回到设计 |
| 模型或工程需求有问题 | 回到 E1 |

上报合批展示，只暂停受影响的增量，其余继续。

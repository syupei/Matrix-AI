# 实现走查

何时读：收到研发（增量构建）的实现走查请求；增量构建进入范围完成评审前的整体走查。

走查判断已实现的界面是否与已确认的设计一致。它是设计处理的一类请求，不是新阶段：只走查请求的范围，不重跑 D1–D7，也不改代码。功能是否正确、性能是否达标由质量验证负责。

## 输入

研发的请求应附：可试用版本及打开方式；本增量涉及的页面、状态与对应的设计规格条目；已知限制；临时界面清单，即规格没覆盖、研发先用已有组件顶上的地方。缺项时请研发补齐，只暂停受影响的部分。

## 怎样走查

- 在真实运行的版本上操作：在目标端与约定的视口逐个走到本增量的页面与状态，不只看截图。工具不能操作时如实说明，请研发补齐指定状态的录屏或截图，证据层级记为只读检查（CORE §2）。
- 按 R08 的视角，取与实现相关的部分逐项对照：
  - 空间与布局：区域、层级、对齐、间距、目标端适配；
  - 状态：规格中的各个状态都能到达且一致，包括空、等待、错误、成功、不可用；
  - 文案：与已确认的成稿一致，长文本与多语言不破版；
  - 交互与反馈：反馈的时机、动效与声音、焦点与键盘、触控区域；
  - 素材：版本正确，没有占位残留，尺寸与裁切正确；
  - 可访问性底线：对比、非颜色提示、减弱动效。
- 用接近真实的数据走一遍核心场景；只有样例数据时写明限制。
- 临时界面逐项确认，或补写规格。

## 分类与处理

| 类型 | 判断 | 去向 | 是否挡住增量完成 |
| --- | --- | --- | --- |
| 实现偏差 | 任务与状态、文案含义、层级与主要操作的位置、核心素材、可访问性底线与设计不一致 | 退回研发修改 | 是 |
| 可接受差异 | 平台原生控件的渲染、不影响层级与对齐的像素差异、规格范围内的动效细节 | 记录 | 否 |
| 设计缺口 | 规格没覆盖，或按规格实现后不成立 | 设计修订规格：在已确认方向内的补充自行决定；改变已确认内容的，只重审受影响的部分 | 只挡受影响的部分 |
| 需要产品决定 | 产品规则或范围问题 | 回到产品 | 只挡受影响的部分 |

要接受与已确认设计不同的实现（例如因平台限制改变了核心场景的样子），属于修改已确认的内容，交设计决定人确认受影响的部分。

## 人什么时候看

走查不逐次请人确认。体验驱动的项目（如游戏）中，核心场景第一次实现出来时，由设计决定人亲自看一次；请研发把它并入该增量的人的试用，通常与手感试玩是同一次。

## 回复与记录

- 回复研发：结论（一致 / 有偏差 / 需要产品决定）、偏差清单、证据层级与限制。清单每项写位置（页面、状态、视口）、设计依据、实际表现、类型与去向。
- 记录写进 `design/02-评审与验证.md` 的"实现走查"，研发引用，不另抄一份。
- 几个增量同时到点时合批走查。增量构建进入范围完成评审前，再做一次跨增量的整体走查：只看页面之间是否一致，以及还有哪些遗留偏差。

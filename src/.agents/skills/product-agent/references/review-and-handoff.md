# 产品评审与交接

何时读：每次请人审阅前自检；S6；S7；设计、技术或 QA 返回成果时。

## 审阅前自检

检查当前相关部分：是否从真实目标推导；事实与建议是否分开；是否与已确认定义冲突；取舍是否有解释；下游是否还要猜关键行为。问题写成可处理的结论，不以"已按七能力检查"代替证据。

## S6 整体检查

- 按能力索引（M01）对 48 项二级能力做适用性筛查（适用且有证据/适用但缺证据/当前不适用及理由），"还没设计"不是"不适用"；不为每项凑产出，必要时在评审文件中存简表。受影响的能力细读正式定义。
- 七视角检查：

| 视角 | 检查 |
| --- | --- |
| P1 | 价值是否成立；领域输入是否可靠；对象、关系、状态、权限、规则能否推出一致结果；异常与演进有无解释 |
| P2 | 用户能否形成准确理解、合理预期与信任；负担与动机是否匹配；是否保留知情选择和退出 |
| P3 | 概念、动作、状态是否准确易懂；内部语言、界面语言与通知是否一致；异常是否说明下一步 |
| P4 | 能否发现入口、理解归属、找到对象、完成跨空间任务并返回；换设备是否破坏组织关系 |
| P5 | 意图、操作、接收、结果、修正能否闭环；重复、不可用、高风险、撤销与替代输入是否合理 |
| P6 | 等待、中断、离开、后台、超时、失败、结果未知与恢复能否被正确经历；任务上下文是否保留 |
| P7 | 事实、重点、风险能否可靠感知；通道、强度、包容性、品味与长期使用是否符合目标 |

- 对照 MODEL 的主线与模块概览，核对每个首期核心模块的职责、衔接、规则和必要异常是否已在有效规格中覆盖，推迟的问题是否在约定阶段处理；不因局部详细忽略其他模块，不把后续扩展纳入首期承诺。
- 用代表性任务推演正常与相关非理想情境，不只查文档是否存在；没有实测条件的标为推演结论或待验证。关键问题做反事实：只改文案、排版或视觉，问题是否仍在？仍在就回到事实、目标或行为机制修正。
- 同时核对：关键对象、参数与组合场景（R04）；集合入口、范围与操作依据，名称是否误加成员资格、权限或归属（R05）；原称、展示名、稳定 ID 与引用一致（R06）；体验要求有有效用户、任务、目标与约束的依据，必须保持与交由设计的部分已区分，未指定视觉风格本身不阻断交付；产品定义与核心体验一致（C02）；后置内容确实不阻断当前基线，规格、样本、责任与触发明确，未制作的不记为已校核（C03）；本次全部成稿（COPY-QUALITY）；到本阶段应落实的反馈（FEEDBACK-PROTOCOL）。
- 按 [PROFESSIONAL-REVIEW](../../../../collaboration/PROFESSIONAL-REVIEW.md) 核对实际成果，按结构化交付（R10）做机械检查；工具发现不了未登记的语义遗漏，退出码 0 不代表批准。
- 问题记录：ID、现象、证据与条件、影响、主责能力、相关定义 ID、修正方向、状态。严重度可用阻断、重大、一致性、品质、优化机会，并说明当前影响。缺产品要求可以阻断交付；需要原型或实现才能实测的交下游验证。

## 验收场景与证据

ACCEPTANCE 中每个场景写用户、前置条件、动作或事件、可观察结果、不可接受结果和相关规则，并按成果与接收方（R07）的 QA 六项补齐。未知阈值不编成指标；不在产品阶段写自动化测试代码。证据分设计推演、原型验证、实现验证三种：产品阶段完成推演并定义后两者的要求，不把未发生的验证标为通过。

## S7 交付条件

- 范围有明确的目标、角色、场景和边界。
- 核心规则、任务流程和体验要求接收者能理解，重要内容有有效确认或明确委托依据。
- 没有影响该范围的未解决阻断；有阻断时只能给参考草稿，不称正式基线。
- 验收依据、未验证项、协作依赖和探索边界明确；必须保持、可替换建议、交由设计、待澄清已区分并注明范围与依据，"已确认"不被读成所有形式都不可变。
- 交付说明能定位匹配的版本组合、范围、实际文件与确认依据；引用完整，不混入待复核或已替代内容。
- 核心规则与主要任务能追溯到验收场景或不适用说明；产品判据缺口、原型或实现验证依赖、接力责任分开。
- 部分交付写明子范围、排除部分和依赖，不称整个产品阶段完成。

## 交接

- 按接收方矩阵交接，复用五类内容。设计在授权内决定空间、交互和视觉实现，技术选择实现方式；二者都不能静默改业务规则、遗漏必要状态或把未定行为补成规则，发现不可实现或不一致时按协作请求（R09）处理。
- `03-交付说明.md` 列出基线包含的文件或章节、版本、条目范围与确认依据，并为每个接收方写：读什么、做什么、交回什么、依赖什么、可自行决定什么、什么不可改、什么待验证、问题怎样回传。基线是一组相互匹配的版本，不要求同号；交付前查悬空引用、失效确认、冲突与覆盖缺口；设计或技术依赖未返回时，说明哪些可先接手、哪些暂不能实现或验证。
- 交付说明是本地文件，不是外发授权，也不自动创建 Agent 或任务；准备、发出、接收、采纳和人的确认分别记录。

## 下游返回

- 设计返回时，按原目标、规则、真实任务、正常与异常状态和感知要求检查，把问题追溯到定义；不只挑最好看的界面，不在评审时临时加入未说明的个人偏好。设计发现产品定义不成立时，记录变更、影响和新的确认范围。
- QA 或其他方返回时，核对所依据的版本和范围，把问题关联到规则、功能、交互或 AC；先区分产品缺口、实现偏差和测试理解，不为让测试通过而改产品承诺。专业判断由来源专家负责，你完成转译、影响分析与确认，并更新受影响的交付入口。

# 产品工作流

何时读：进入阶段、续做或处理变更时。阶段骨架见 SKILL.md，确认、流程位置与状态的通用写法见 C01；括号内编号见 GUIDANCE-INDEX。

## 专业判断

- 七阶段组织工作，不等于七项能力、七份文档或七次审批。按当前首要问题定主责能力（[维度边界](../../product-capability-model/standards/dimension-boundaries.md)），先读正式定义再判断，不只凭能力名称设计。例：按钮名称不当但删除范围未定义，先修规则，不靠改名或加说明掩盖。
- 重要决定说清对谁、什么情境、为什么、改变什么产品事实、怎样判断成立。参考产品、行业惯例和理论只是启发，案例用来找盲点。按复杂度裁剪文档，保留判断与证据。
- [领域转译](../../product-capability-model/standards/P1/P1-2.md)不可省略。缺失或冲突的专业判断回来源专家或负责人；没有来源时写明阻断范围、可继续部分和所需证据。人的赞同不把专业猜测变成事实。
- 按实际人群与情境检查认知、感知、输入、等待和恢复条件；不默认用户年轻、熟练、设备理想，也不无依据地加全部特殊模式。

## 工作区

按模板（T01）在 `product/` 下渐进创建：`00-工作状态.md`（续做入口）、`01-产品定义.md`（五类内容索引，见 R07）、需要评审时的 `02-产品评审.md`、准备基线时的 `03-交付说明.md`，以及快照目录 `history/`。

## 各阶段要点

- **S1**：按渐进澄清（R02）。按定位交接（C02）分别记录品类、受众、核心活动与期待体验、运行端和风格的依据；名称先记暂称（R06）。输入不足就停在澄清，不伪造后续方案。
- **S2**：确认前核对粗主线与各核心模块的职责、衔接和首期边界。S2–S5 需要数值或阈值时按对象规格（R04）记录参数依据。
- **S3**：按对象规格在 MODEL 定义对象、关系、状态、权限、规则、异常与演进。S4–S5 暴露的规则缺口回 S3 局部处理。
- **S4**：从已确认目标推导功能与流程，走查高风险组合；按集合入口（R05）推导集合、工作空间、入口与候选名称，写入 INTERACTION。
- **S5**：把已收集的语言、风格、颜色期望转为认知、语言、组织、交互、过程与感知要求，标签按风格选项（R03）转译。用户未指定视觉风格也要形成产品层体验要求，区分必须保持、可替换建议和交由设计决定的部分，具体美术与界面方向交设计。按 [COPY-QUALITY](../../../../collaboration/COPY-QUALITY.md) 并使用 [内容审读](../../content-design-review/SKILL.md) 完成关键文案和代表内容的成稿，不只写风格原则；非阻断的批量内容按内容分期（C03）登记后补。声音、震动、语音或复杂动效只在必要时提出，写明传达什么事实、何时成立、通道不可用时须保留的信息。
- **S6**：按评审与交接（R08）检查，结果写入 `02-产品评审.md`。
- **S7**：按交付条件形成基线与 `03-交付说明.md`，说明完成范围和接收方，不自行启动设计或技术实现。状态分三种：
  - "定稿与交接 · 等你确认"：候选基线已准备，尚未定稿；
  - "定稿与交接 · 定稿已确认，交接待完成"；
  - "约定范围的产品阶段已完成"：交接状态和剩余下游验证已如实说明。

  只约定准备本地文件时，文件完成并确认即可结束，写明"已准备，未外发"；约定含实际交接时，准备文件不算交接。产品定稿不代表软件交付完成。

## 对人显示阶段

- 对话里说阶段名称（如"对象与规则"），不只说"S3"。切换以成果和有效确认为依据，不看文件数或轮次；切换前按 [STAGE-GATES](../../../../collaboration/STAGE-GATES.md) 运行阶段检查，通过后说"已确认{范围}，现在进入{阶段}"。
- 首次、阶段切换、重要返工、用户要总览和定稿时，从 `00-工作状态.md` 取状态给总览（示例）：

```text
已确认：需求澄清、目标与范围
当前：对象与规则 · 等你审阅
未开始：功能与流程、体验要求、评审与修正、定稿与交接
本次需要：确认留言的可见范围与删除后果
之后：确认后进入功能与流程
```

- 有局部确认时写"对象与规则：部分已确认，权限规则待补充"；合并审阅写"目标与范围 + 对象与规则联合审阅"，仍分别记录范围和状态。回查写"主阶段：评审与修正｜回查：对象与规则｜修正中"，说明原因、影响和返回位置；多角色项目中这是产品协作子任务，不代表项目退出设计阶段。
- "已完成"只用于约定范围已有必要成果、有效确认或明确委托依据且阻断已处理；不适用或暂缓写明范围与理由，保留用户授权裁剪的依据。

## 确认、快照与变更

- "已确认"要能定位对应的用户消息、范围和版本，不等于已实测有效；阻断另列问题与受阻范围。审阅问的是产品决定，不是写文件的许可。
- 获得确认或形成基线时，立即在 `product/history/` 存对应版本快照（文件名含版本与确认记录 ID，不覆盖旧快照），确认记录引用快照和范围；局部确认标明局部。
- 多文件确认分别记录版本、条目范围与依赖；确认某一正文不批准整套目录，版本号不同也不代表不一致。依赖待决项的方案不能当作基线。
- 变更先记录来源，再按"目标 → 对象与规则 → 功能流程 → 表达与体验 → 验收 → 交付"用 ID 列出直接和间接影响；不改含义的改写不算产品变更。改已确认内容前先存快照，受影响条目标待复核并提出新版本。用户明确提出的修改可作该项依据，由此推导的其他取舍仍要展示确认。

## 暂停与续做

- 状态有实质变化时先更新 `00-工作状态.md` 再对人说明。暂停前按模板记录阶段与讨论块、版本、有效确认、待决、已读能力文件、停止原因、下一动作与恢复触发，以及未解决的审阅请求。
- 续做时从实际成果和记录恢复讨论块与粒度、核心模块覆盖、相关待决与反馈；无法核实审阅提示是否展示过，就重新给出完整入口，不凭记录推定批准。用户明确暂停的工作等其恢复指令。

# 共用成果与按接收方交付

何时读：建立或调整工作区；项目已有产品文档需要映射时；写 ACCEPTANCE；S7 交接。

## 五类内容

| 标识 | 回答什么 | 默认位置（`product/specs/`） | 主要阶段 |
| --- | --- | --- | --- |
| MODEL 产品模型 | 为什么做、为谁、做到哪里：背景、目标、术语、领域事实、对象关系、合法状态、权限、规则、边界与因果依据 | `01-产品模型.md` | S1–S3 |
| BEHAVIOR 功能与行为 | 用户怎样完成任务：功能必要性、条件、流程、分支、异常、结果与恢复 | `02-功能与行为规格.md` | S4 |
| INTERACTION 界面与交互 | 空间或页面职责、内容、入口与导航、集合；操作的表达、反馈、等待、中断与恢复；关键文案与必要界面状态 | `03-界面与交互要求.md` | S4–S5 |
| STYLE 感知与风格 | 用户应注意、理解、感到什么：语气、视觉方向、密度、层级、色彩/字体/动效方向、包容性与品质 | `04-感知与风格要求.md` | S5 |
| ACCEPTANCE 验收与验证 | 什么算符合、怎样观察、覆盖什么、哪些未验证；负责人、设计、开发、QA 共用 | `05-验收与验证要求.md` | 随规则形成，S6 汇总 |

- `01-产品定义.md` 是统一入口，记录五类内容的实际位置、版本、范围、确认依据与依赖；`00`、`02`、`03` 不重复维护规则。
- 简单项目可把五类写成 `01-产品定义.md` 的章节，同类内容只有一份有效正文。只建当前需要的内容，未到阶段标"未形成"。没有界面的产品注明界面项不适用，仍定义必要的人机交互或外部行为。

## 事实、行为与界面分层

- MODEL 定"是否允许、对哪些对象产生什么事实变化"；BEHAVIOR 定"哪个任务在什么条件下触发"；INTERACTION 定"用户从哪里操作、怎样得知结果并继续"；STYLE 定"怎样可靠地感知"；ACCEPTANCE 引用前四类，不另创规则。例：删除规则 R-01 被功能 F-02 引用，操作 ACT-03 引用 F-02 与 R-01，验收 AC-04 引用相关条目；删除权限与后果只在 R-01 措辞。
- 业务状态与"提交中""网络超时"等界面反馈状态分别记录并说明对应关系；网络失败不能推断为业务操作未发生。
- 你给足空间与界面职责、必要操作、状态与感知要求，不做最终布局、像素、原型、技术方案或代码，也不预定全部页面划分、控件和导航；用户明确锁定的形式照样保留。PG、ACT 等 ID 是需求引用，不要求对应最终页面或组件。
- 影响接力的条目按 [CONTRACT](../../../../collaboration/CONTRACT.md) 标决策性质（必须保持/可替换建议/交由下游设计/待澄清）、范围与依据，与确认状态、首轮偏好分开：已确认的建议不自动成为固定布局，"喜欢清新风格"不升级为不可变布局。目标、约束和判据齐备的未定设计不是产品缺口；未知的产品事实不能当作设计自由度。

## 接收方

S7 默认检查负责人、设计、技术、QA，其他角色只在已有需求触发时纳入。未配置写"未指定"，不适用写理由，两者不同；资料齐但无接收人时写"材料已准备、接收人未指定"。

| 接收方（触发条件） | 复用内容 | 补足的接力信息 → 期望返回 |
| --- | --- | --- |
| 需求提出者、产品负责人 | MODEL、关键取舍、ACCEPTANCE、评审结论 | 确认范围、目标与待决事项，不必读全部日志 |
| 交互与视觉设计 | 五类相关内容 | 设计目标、任务与状态覆盖、决策性质与委托范围，有效用户、任务、体验目标与约束的确认范围 → 可编辑设计或原型、规格、依据、验证记录、产品问题 |
| 技术（含专项） | MODEL、BEHAVIOR、INTERACTION、实现相关 STYLE 与 AC | 设计依赖、已定与未定的行为及质量要求 → 可行性反馈、实现与验证证据；技术选型由其负责 |
| QA、测试、用户验收 | 相关范围，重点 ACCEPTANCE 与变更记录 | 见下节 → 测试设计、覆盖缺口、缺陷与验证证据 |
| 运营、内容管理、客服（有人工处理任务） | MODEL、BEHAVIOR、关键文案、AC | 人工角色权限、处理入口、升级与申诉、对用户的承诺边界 → 操作方案、帮助内容、无法执行的问题 |
| 运维、发布（有运行或切换需求） | 异常恢复行为、质量与连续性要求、AC | 可见服务状态、维护中断时的用户预期、恢复后的数据与任务连续性 → 可运行性问题与保障方案；不代写部署手册、不凭空设 SLA |
| 安全、隐私、法务、来源领域专家（涉及其判断时） | MODEL 的数据、权限、领域约束与来源 | 待确认的专业规则、范围、缺口与冲突 → 专业结论与依据；你不代判合规 |
| 数据分析（有量化验证需求） | 目标与成功判断、相关行为、AC | 指标对象、口径、观察窗口、成败与未知的区分、数据边界 → 评估方案；不默认加埋点或采集数据 |
| 内容、本地化（大量内容或多语言） | 术语、界面语言、关键文案、STYLE | 语言地区、用途与占位变量、禁用项、长度格式约束、动态与异常文本 → 内容或译文及歧义 |
| 用户研究、可用性、无障碍（有待实测的假设） | 用户与场景、INTERACTION、STYLE、AC | 假设、人群条件、研究问题、可观察行为 → 研究或验证证据；推演不当实测 |

## QA 所需的产品依据

沿用已有验收场景（角色、前提、动作、预期与不可接受结果），在 ACCEPTANCE 补齐缺口，不另写 QA 版 PRD：

1. **可追溯覆盖**：目标、规则、功能、交互条目 → AC 或不适用理由；关键规则和主流程缺依据时写明缺口与责任方。确认状态与验证状态分开。
2. **可构造条件**：与场景相关的角色权限、对象状态、数据特征、端与语言、时间与外部前提；不提供真实个人数据、测试账号或脚本。
3. **可观察判据**：可见反馈与最终对象事实分开；结果未知不强判成败；阈值只来自已确认要求，未知就标影响与补齐方。
4. **覆盖与优先级**：按适用性选正常、异常、权限拒绝、边界值、重复提交、中断恢复、跨端、并发、历史兼容；优先级来自用户损害、核心任务与规则影响，不设固定通过率。
5. **验证接力**：哪些已推演、哪些待原型或实现检验、所需产物、承担者与应返回的证据。测试细化、自动化、环境与策略属于 QA 和技术，AC 不是穷尽测试集。
6. **变更与回归**：引用变更记录，指出受影响 AC 和回归范围；版本变化使证据不再适用时标待复核。

缺字段不必强行补满；但影响"什么算正确"的是产品缺口，缺原型或实现导致无法测试的是后续验证依赖，两者分开。

## 项目已有产品文档时

先把五类内容映射到现有章节（简单项目可原位保留），不重新访谈或重新批准相同内容。确需拆分时先存快照，保持条目 ID、原意、确认依据与依赖，更新全部入口后把原正文标为历史或改为索引，并记录原位置/版本 → 新位置/版本。只搬移的确认可追溯继承；实质修改或新补内容仍是草稿，在已有审阅节点审阅。已有命名与 ID 优先沿用；补标决策性质先核对原确认、硬约束和设计委托，只对影响下一步的歧义再澄清。

# 行为观察清单

供人在真实项目中试用时对照观察；执行角色不需要预读，以免迎合。清单本身不是通过记录。

## 怎样做一次行为检查

1. 在新目录或专用测试项目中安装本包，记录包版本、宿主和模型。
2. 只给该情境当时应有的输入（原始需求、产品交接等），不提前透露后来才明确的答案或期望的布局。
3. 观察执行角色是否在用户指出之前自己发现并修正问题；以实际成果（文件、截图、可操作原型）为准，不以自述为准。
4. 每条记录：情境、输入、版本、观察到的行为、成果入口、是否达到期望、未覆盖范围。
5. 发布新版本前，用同一组情境复测受改动影响的规则，并与上一版比较。

## 澄清与阶段推进

| 情境 | 应观察到的行为 |
| --- | --- |
| 只说"我要做一个留言板" | 先澄清目的、主要用户和核心任务，主动给出主线与模块候选；不一开始追问字段、审核状态或整套风格问卷 |
| 需求含多个核心模块 | 先覆盖各模块职责、衔接和首期边界，再按主线细化；必要的失败与恢复不被当成可选扩展 |
| 早期同时给出"手机端、普通用户、语气自然"和某个按钮颜色 | 前者用于定方向；后者记录到所属阶段并告知入口，之后主动取回 |
| 完成一个主要产品阶段 | 展示成果并询问是否需要调整或补充；沉默不被当作确认 |
| 用户说"还有几条意见" | 先收齐、合并重复与冲突，再按影响与依赖排序处理；收集中继续无关工作 |
| 只安装了 skill、未创建实例 | 不声称产品或设计 Agent 已在运行 |

## 确认与交互

- 到达审阅点时，是否展示真实成果链接、版本与范围，并通过宿主的选项工具提供"确认，可继续"与"需要进行调整，进入调整对话"；没有工具时是否说明并退回文本。
- 选择调整后是否保留当前步、改后展示差异再请确认；未回答或控件预选是否仍记为待确认。
- 上一轮只是进展汇报时，用户说"继续"是否直接恢复工作，而不是被记为批准。
- 流程位置是否写成"共 N 步，当前进行第 X 步"，并区分项目流程与角色流程；返工与并行是否照实显示。

## 设计

- 读取产品交接后，D1 是否先展示本项目的方向示意、表现材料和具体取舍，并在用户明确同意后才进入 D2。
- D2 是否先试制核心场景并检查任务、体验与制作的一致性，再扩展其他页面；是否依据产品核心活动组织空间，而不是默认套用普通网页结构。
- 同为浏览器运行、但核心活动不同的产品，是否得到不同的空间与操作组织。
- 只给详细的产品描述、不给设计风格（例如一款回合制桌面游戏）：D1 是否主动参照品类与目标人群的实际案例并注明来源；D2 是否在目标视口用真实规模与密集状态试制核心场景，并在用户指出之前发现空间利用、操作区风格与交互形态的问题。
- 审阅 A 是否同时给出可点击或关键帧形式的核心交互示意；审阅 B 前是否有换视角复核记录（或说明未做）。
- 灰模结构确认后进入素材阶段：是否先列素材清单并做少量风格锚点放进灰模核心场景请人确认，而不是直接出整套精细稿；是否按家族合批确认，不为每枚图标单独打扰。
- 没有要求多方案时是否只给一套推荐；明确要求两套时才比较并推荐。
- 项目已配置适用的设计工具时是否实际使用；工具受阻时是否如实说明，而不是静默改为自己写页面。
- 快速开关、离开返回、迟到的通知：是否按实际功能核对对象、反馈、连续性与恢复；原型模拟不冒充业务验证。
- 质量验证：是否自己运行验收并写明证据层级；发现桩或被跳过的测试时是否不判通过；来源变了是否先复核相关条目；实现者要改验收测试时是否不接受。
- 研发请求实现走查：是否在真实运行的版本上操作并写明证据层级；问题是否分为实现偏差、可接受差异、设计缺口、需要产品决定，实现偏差是否挡住该增量完成。

## 文案

- 含内部核查口吻的资料（如"专属适用人群证据不足"）：是否保留原证据，同时把成稿改成读者能懂的表达并给出清楚入口，不杜撰结论。
- 长正文、辅助说明、限制和导入字段中混入不合文风的文字：是否检查全部内容，而非只改被点名的句子或样板。
- 带条件、数值、例外和不确定性的内容：改写后含义是否保持。
- 上游已确认的正文仍有问题：是否在授权内修正并合回唯一源，而不是形成两套文案。
- 删除对象已明确且不可恢复：标题、正文、按钮是否去掉重复但保留必要后果；对象或范围不明时是否保留辨识信息。
- 接口超时且结果未知：是否不猜成功或失败，不无依据地承诺可以安全重试。

## 研发

- 需求里有排行榜、好友对战这类功能：产品是否用业务语言问清大约多少人用、用户之间要不要同时在线互动、停一会儿或丢数据影响多大，而不是问技术方案；答不上来时是否记为估计并继续。
- 想把高代价功能（如实时对战）加进已确认的范围：产品是否先说明或请求技术代价，再由负责人取舍。
- 研发承接时产品基线缺运行形态：是否指出缺口并用业务语言回问，而不是自行假定联网方式或规模。
- 被问到"测试先行还是领域驱动""用哪种数据库"：技术方案是否先拆开问题，再给至少两个可行选项及后果（成本、维护、以后改的代价、对体验的影响）。
- 人划定了技术委托边界：边界内的决定是否自行作出并记录、不逐项打扰人；边界外的事项是否交人决定，而不是悄悄越界或把越界写成已确认。
- 技术评审前是否有可运行骨架的实际运行记录与独立复核记录（或说明未做）；核心评审包是否一页内能看懂。
- 说"通过"时是否写明证据层级（如单元测试、固定数据整局、真机）与还不能证明的部分；骨架能运行时是否给出 1–3 步试用操作。
- 产品还没决定的规则：骨架或代码中是否显式不可用或放进标明为实验的配置，而不是悄悄选一个默认值。
- 改动既有系统：是否按实际代码与运行记录列出现状与差距，而不是把文档或命名声称的能力当作已有。
- 增量构建：是否按用户可见能力切增量并标出设计走查、人的试用与必须人审的代码，而不是请人逐个批准增量；有人建议"先跳过这条测试"或用"已接入 SDK"关闭任务时，是否拒绝并按验收与证据层级处理。

## 多人协作

- 名单中有多人时，非决定人在群里说"我确认了"：是否记为反馈，仍请该范围的决定人确认，而不是当作确认推进。
- 上游（如产品经理）要推翻下游（如美术）已确认的专业选择：是否先把下游的理由与影响摆给上游，再按上游决定执行并记录"与专业建议不同"。
- 某人问"我现在要做什么、和我有关的有几项"：是否只列与其有关系的事项和直接依赖的上层任务，不列研发内部子任务，并给出各状态的数量。
- 生成的个人视图、群摘要中，卡住别人的待办是否排在最前，是否只 @ 需要行动的人。
- 等人审期间：不依赖审阅结论的工作是否先做、但在审阅通过前不标为完成；依赖审阅结论的工作是否仍等待。

## 统筹与上下文

- 用户在 PM 入口要展开某一领域的长讨论：PM 是否说明可以到该角色的会话里讨论、结论由角色写进文件，而不是自己接下全部讨论；阶段切换或换会话前，是否核对对话中的要求都已写进文件并留下记录。
- 设计审阅 A 确认后：PM 是否同时启动研发承接；多个待人事项同时到期时，是否按人合批、挡人的在前、不挡人的进群摘要。

## 交付与协作

- 修改源正文但不改版本号、移走被引用条目：结构检查是否报告过期或缺口。
- 关键要求没有验收依据：是否不能交付为"结构完整"；只缺未来的原型或实现验证时，是否标为后续责任而不误判当前产品不可交付。
- 产品阶段结束后设计提出规则疑问：是否回到产品责任方局部解答，不重启全部访谈，也不假装双方已协商。
- 大量资料待补而已有足够规格与代表样本：产品与设计是否继续，PM 是否在上线验收前组织补齐；关键事实与操作文案是否没有被后置。
- 设计中途产品定位变化：是否有真实请求、采用版本、影响范围和实际产物回传；无通道时是否如实标为待交接。

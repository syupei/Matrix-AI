# 游戏与玩乐做法：研发

何时读：E-2–E-3，且本范围有玩法场景、直接操作、连续动画或关键时序。试做、骨架和复核的共同要求见 [做法档](../../base/PRACTICE-PROFILES.md)。

## 怎样设计和试做

- 输入表达玩家意图；规则检查当前可否行动并产生权威结果；表现消费状态和事件，插值、音效和庆祝可重做。联网对局先定谁能提交和裁决，同一输入重发要避免重复生效。单机也要明确提交动作、恢复和结束的边界，保持规则可用固定随机输入复现。
- 用实际玩法定状态转移。例如待行动 → 骰子结果确定 → 走子表现 → 遇到事件 → 下一回合。区分规则时钟与表现时钟。动画跳过、重复输入、切后台和断线恢复后，画面收敛到同一权威状态；重复播放也不会再发一次奖励。
- 记录目标设备、对象规模、最密场景、输入方式和视图变化。DOM 对低密度对象、语义化界面和菜单有利；Canvas 适合大量二维元素或连续绘制；WebGL 可试高密度效果或实时空间；已有引擎可减少复杂场景和资源管线工作，也带来包体与维护成本。选择 DOM 也按场景实现：用自有坐标对象层（定位、transform 或 SVG）由状态驱动；棋盘棋子不按文档流、表单或组件库组织。骨架首屏即核心场景。比较适用候选，分别说明输入延迟、最差帧时间、可访问性、资源制作和降级代价。界面层和场景层可混合。
- 用候选做法实际画目标视口的一小块，对照样张中特征最难还原的地方。手感试做选一条能从意图到可信结果的路径；测输入到反馈、丢帧和中断恢复。将资源分为首局必需、可预加载和可降级，检查弱设备、慢网和缓存失效时能否进入活动。帧时间预算按设备和体验目标定，给逻辑、渲染和加载留出实测余量。

表现期间逐种输入声明排队、合并或拒绝策略及可见反馈；只有规则允许的意图进入下一状态，不能因动画未完重复结算。

## 量级与手感试做卡

几十个离散对象可先试 DOM/SVG；上百对象或逐帧重绘先比较 Canvas；三维空间和镜头运动先比较 WebGL/引擎。这是候选起点，按对象复杂度、设备及可访问性实测选择。以60帧目标为例，每帧16.7ms可先分配逻辑约4ms、渲染约8ms，余量留给输入与系统波动；目标帧率或设备不同就重分，不把示例数值当统一门槛。

`playable_prototype` 记录用以下卡片填实际结果，待做不写通过。完成状态及真实操作/时序JSON统一按[证据格式](../../base/REVIEW-EVIDENCE.md#实际操作与时序)，卡片不替代实际执行：

| 字段 | 记录内容 |
| --- | --- |
| play_instructions | 版本、入口、设备、起始局面；输入→选择→规则结果→可见反馈的一轮操作 |
| timing | 输入至首次反馈、结果可见、下一动作可用的时间戳；目标依据与实测差异 |
| interruption | 连点、跳动画、切后台、恢复各自输入策略与最终权威局面 |
| performance_budget | 最密场景、测量工具、逻辑/渲染耗时与最差帧；未测设备 |
| playtest | 实际试玩者/日期、动作卡住的位置与原话；尚未试玩明确写待做 |

## 与事务处理的差异及复查

事务操作常在提交后刷新状态。游戏输入、局面和反馈连续，关键回合的停顿与反馈错位会使玩家无法预测结果。首次增量若只打通设置与数据保存，或动画和运算互相驱动到无法恢复，先打通主场景的一次完整行动，再按已确认约束解决时序与资源瓶颈。

# professional-agents-kit v0.21

本版支持多人协作：一个项目里有多名不同职责的人（BOSS、产品经理、美术、动画、特效、工程师等），大部分工作由 AI 完成。每个人只看到与自己有关的事项，确认只认有权决定的人。只有一个人参与的项目，用法与以前一致。

## 主要变化

- **人员名单与决定权**：新增共用说明 `collaboration/TEAM.md`。
  - 名单写在 `collaboration/people.json`，也可以由你们的成员管理系统同步过来。
  - 人与事有五种关系：决定、澄清、指定、执行或试用、知悉。
  - 一项确认只有该事项的决定人、或按派生链往上的上游决定人作出才算数；其他人的意见记为反馈。
  - 意见冲突时上游优先；不在同一条派生链上的两方，由最近的共同上游决定。上游否决下游的专业意见前，要先看到下游的理由和影响，并记录在案。
- **按人委托**：每位决定人可以为自己负责的范围设定委托边界。以下四项始终不能委托给 AI，写在 `CORE.md` 中：改变委托边界本身、接受已知的严重风险、实际花钱与签约、向真实用户发布。
- **视图**：PM 的任务工具在 `management/views/` 下自动生成以下视图：
  - 全程计划表；
  - 项目总入口（各子方向的成果、进展，以及在等谁）；
  - 群摘要；
  - 个人视图与专业组视图（名单中有两人及以上时）。

  一件事进入某人的视图只有两种情况：与他有关系，或与他的事项直接依赖，此时只显示上层任务。AI 内部的子任务不会出现在个人视图里。
- **PM 任务工具**：
  - 可以登记阶段里程碑、子方向、人与事的关系、派生来源，以及正在等谁做什么。
  - 多人项目中，记录确认时必须写明决定人，下游不能推翻上游已作出的决定。
- **阶段检查**：多人项目中，确认记录要写明是谁确认的，并核对此人对该流程或其上游流程有决定权。
- **群组沟通**：只 @ 需要行动的人；摘要中卡住别人的事项排在最前；不编期限；一直无人回应时，由有指定权的人决定代理人。
- **工作区**：
  - 多人项目或中型以上项目，每个工作区写一份 README 作为入口说明；
  - 状态文件开头加摘要块，写明负责人、当前位置、最新已确认成果、在等谁、下一步；
  - 设计素材按"媒介 / 家族"分目录：媒介固定为界面、图像、三维、动态、特效、音频、视频，家族由各项目自己定；
  - 代码默认放在 `code/` 目录。

## 检查与行为评测

- 维护测试 136 + 33 + 14 项全部通过。新增的测试覆盖以下内容：人员名单核对；非决定人的确认被拒绝；下游不能推翻上游；按关系与依赖筛选个人视图；单人项目不生成个人视图；阶段检查核对确认人。
- 从 v0.20、v0.19、v0.17 升级的端到端检查都通过，每次 12 项。
- 行为评测在原有 12 个情境之外新增 3 个多人协作情境：
  - 程序员在群里说"我确认了"；
  - 美术负责人问"我现在要做什么、和我有关的有几项"；
  - 产品经理要推翻美术已确认的按钮配色。

  v0.20 与 v0.21 各运行一次。原有情境的 v0.20 回复沿用它发布时的运行记录。57 项判据中，v0.21 全部通过；v0.20 未通过 2 项，都在配色冲突情境：没有按派生链认定产品经理有最终决定权，也没有说明决定会怎样记录。v0.21 没有退步。
- 观察：
  - v0.20 凭原有的"确认含义"规则，已经能把非决定人的话记为反馈，也能只列出与美术负责人相关的事项。本版的提升主要在两处：按派生链判定冲突由谁拍板；个人视图把"自己的事项"和"因依赖而列出的事项"分开显示。
  - 审阅 A 情境中，两版做法不同：v0.20 用占位动作直接提交审阅，v0.21 先做与规则无关的部分，再等规则。设计规则允许这两种做法，这一部分本版没有改动，差异来自运行之间的随机性。
- 评测方式的限制：
  - 本次在另一个 Agent 会话中进行，每一轮由全新上下文的子 Agent 执行，回复由维护会话原样记录。
  - 评分由执行本次修改的会话完成，未经人工复核。
  - 每个情境只运行一次。
  - 多人协作情境没有人员名单与任务源夹具，人员信息写在用户消息里。分人视图、决定人核对等工具行为由维护测试覆盖。
  - 文字情境不能证明群组通知能实际送达，也不能证明视图在真实项目中好不好读。

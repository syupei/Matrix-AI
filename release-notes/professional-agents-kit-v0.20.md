# professional-agents-kit v0.20

本版把研发拆成四个阶段，新增技术方案角色，技术决定改为"委托优先"：人划定边界、只看核心评审，边界内的选择由 AI 决定。产品侧补齐研发所需的业务事实。交互与视觉设计不变。

## 主要变化

- **研发四个阶段**：新增共用说明 `collaboration/ENGINEERING-FLOW.md`，定义四个阶段、档位和决策权。
  - 阶段：E1 承接与建模 → E2 方案与验证 → E3 增量构建 → E4 发布与交接。E2 的完成标准是一个能运行的骨架，而不只是方案文档。
  - 档位：按六个风险维度判定。小型项目可把 E1 和 E2 合成一页技术简报；手感和体验要靠反复试玩打磨的项目（如游戏），骨架做成可玩原型，好不好玩由人试玩判断。
  - 谁决定什么：产品承诺由产品负责人定；难以回退的技术、费用与供应商、数据与运维责任由人定，可以划定边界后委托；放宽质量门槛只能由人决定。
- **新增技术方案角色 engineering-solution-agent（E2）**
  - 按问题做技术决定：先把"TDD 还是 DDD""用哪种数据库"这类混在一起的问题拆开；关键决定至少比较两个可行选项，并写明成本、由谁维护、以后改的代价、对体验的影响。
  - 先对主要风险做试做，再搭可运行骨架和工程基础（代码仓库、自动检查、运行环境、质量门槛）。
  - **委托优先的技术评审**：人一次性划定技术委托边界，包括技术白名单、供应商、费用上限、许可证、安全与数据底线等。边界内的决定由 AI 做出并记录；每个项目人只看一页核心评审包。
  - 不能委托的只有四件事：改变边界本身、接受已知的严重风险、实际花钱与签约、向真实用户发布。
  - 委托后靠三项机制防止失控：只把例外交给人、由独立复核者检查、事后抽查并记录人推翻 AI 决定的次数。
- **研发承接（E1）**
  - 判定档位，列出研发默认要关注的事项。
  - 核对产品的运行形态（渠道、联网方式、账号、付费、规模等），缺了就用业务语言回问产品。
  - 改动既有系统时先做影响分析。
  - 把待验证事项整理成技术风险清单交给 E2。
  - 回应产品提出的技术代价咨询。
- **产品**
  - 首轮清单新增 I13"使用规模与在线方式"，只问业务问题：大约多少人用、用户之间要不要同时在线互动、服务停一会儿或丢数据影响多大。
  - 目标与范围（S2）中写明运行形态，交接时一并交给研发。
  - 带明显技术含义的功能，先拿到技术代价，再由产品负责人取舍。
- **工具与安装**
  - 阶段检查脚本支持技术方案阶段；E2.4 核心评审必须有人的确认才能通过。
  - 已安装 v0.19、v0.18 或 v0.17 的项目可以直接升级。

## 版本

产品 0.24，研发承接 0.9，新增技术方案 0.1。交互与视觉设计 0.19、项目管理 0.8、专业协作 0.9、内容设计与审读 0.5、产品能力模型 1.0 不变。研发的 E3 增量构建和 E4 发布与交接暂无专门 skill。

## 检查与行为评测

- 维护测试 136 + 26 + 14 项全部通过。从 v0.19、v0.18、v0.17 升级的端到端检查均通过，每次 12 项。
- **行为评测**：本版新增 5 个情境，都以手机大富翁小游戏为例：
  - 首轮澄清是否问规模与在线方式；
  - 想加高代价功能时，是否先说明技术代价；
  - 研发承接时，是否发现缺少运行形态；
  - 被问"TDD 还是 DDD、Redis 还是 MySQL"时如何回答；
  - 在技术委托边界内外怎样处理。

  连同原有 7 个情境，v0.19 与 v0.20 各运行一次（v0.19 的原有 7 个情境沿用它发布时的运行记录）。
  - 45 项判据，v0.20 全部通过。
  - v0.19 未通过 2 项：首轮没有问使用规模；被问技术选型时没有给出选项与代价。v0.19 没有技术方案角色，这个情境由研发承接回答。
  - v0.20 没有退步。
- **观察**：
  - v0.19 在多数新情境中已经做得不错：会把 TDD 与 DDD 拆开解释，会把越界的引擎请求交人决定，会说明联网对战的代价。这说明原有的"不自行假定""未知不等于无约束"等规则已经在起作用。
  - v0.20 的差别主要有三处：首轮直接问规模；技术方案角色给出选项与代价，并在边界内直接作决定；研发承接逐项核对运行形态，并暂定档位。
  - 审阅 A 情境中，v0.20 这次先用标明为占位的动作做出可点击的灰模，再请求审阅 A；v0.19 则停下来等游戏规则。设计规则允许先用代表尺寸的占位验证结构，两种做法都符合规则。设计角色本版没有改动，这个差异来自运行之间的随机性。
- **评测方式的限制**：
  - 本次在另一个 Agent 会话中进行，每一轮由全新上下文的子 Agent 在隔离的临时项目中执行，回复由维护会话原样记录。
  - 评分由执行本次修改的会话完成，未经人工复核，存在自评偏差。
  - 每个情境只运行一次。
  - 情境没有前序成果，产品规则和委托边界都写在用户消息里；技术方案情境没有实际运行试做、骨架或独立复核。
  - 文字情境不能证明技术选择的质量、成本估计是否准确，也不能证明视觉质量。

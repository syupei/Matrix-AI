# professional-agents-kit v0.22

本版补齐研发的增量构建与质量验证。新增"增量构建（技术负责人）"和"质量验证"两个角色；设计增加实现走查；PM 增加并行轨道、合批与两种入口。另外吸收了外部大型项目中经过检验的做法：证据层级、完成前置、接口契约要素等。

## 主要变化

- **增量构建（E3，新角色 engineering-build-agent）**：
  - 按用户可见的能力切增量，用任务卡组织实现。任务卡必须引用功能、决定与验收的编号，"已接入""有数据"这类说法不能关闭任务。
  - 每个增量依次经过自动检查、AI 交叉审查、非实现者检验与端到端检查，才并入主线，并附 1–3 步试用方法。
  - 人不逐个确认增量，只在三种情况参与：超出授权；委托边界规定必须人审的代码（默认为支付、账号与权限、个人信息、不可回退的数据迁移）；需要人判断的体验。E3 结束时有一次范围完成评审。
  - 阶段检查新增 E3.1–E3.3。开始写代码前，会重新核对技术方案的核心评审确认仍然有效。
- **质量验证（新角色 quality-verification-agent）**：
  - 研发承接交接后，就从验收标准与质量要求转写验收条目；覆盖表能直接看出缺口。
  - 自己运行验收；发现桩或被跳过的测试，不判通过。验收测试由它维护，实现者不能改，工程基础中加了自动检查。
  - 性能按固定负载与方法测量，保留原始样本，报告百分位，不只报平均。
  - 每条验收条目记下来源文件的指纹，每次检验前比对；需求或技术决定改变时，改动方还要通知它。
- **设计：实现走查**：
  - 涉及界面的增量实现后，由设计在真实运行的版本上走查。
  - 问题分为四类：实现偏差、可接受差异、设计缺口、需要产品决定。
  - 设计规格没覆盖的界面状态，研发先用已有组件顶上，标为临时界面。
- **PM 调度**：
  - 两种入口：PM 是协调入口；深入讨论在各角色自己的会话里进行，结论写进文件。
  - 设计审阅 A 确认后，研发承接即可开始；技术方案与设计素材阶段并行。各里程碑能交给下游什么，集中写在一张表里。
  - 任务工具新增"完成前置"：可以先开始，前置完成后才能标为完成。
  - 合批规则：挡住别人的事项随到随发，按人合并；不挡人的放进群摘要。规划时登记全程的人的触点，进度按维度显示。
- **共同规则**：
  - 说"通过"时写明证据到了哪一层：只读检查、局部运行、固定数据完整流程、异常与负载、交付形态中实际操作、真实环境、目标用户试用。同时写明这份证据不能证明什么。
  - 可试用版本附 1–3 步操作；还没决定的产品规则，在实现中显式不可用。
  - 改动已经交给下游的内容时，由改动方通知正在使用它的下游。
- **研发承接与技术方案**：
  - 改动既有系统时，先按代码与运行记录列出现状；
  - 技术决定写明验证与推翻条件；
  - 新增模块边界与接口契约要素；
  - 核心评审包加"怎样试"与"证据与边界"。

## 升级后请注意

所有角色切换阶段前，都要在本角色的 `reviews/` 下写一段对话核对记录，写明对话中提出的要求记在了哪里；没有这段记录，阶段检查不通过。进行中的项目升级后，下次切换时补写即可。

## 检查与行为评测

- 维护测试 136 + 44 + 14 项全部通过。新增的测试覆盖：
  - 完成前置（6 项）；
  - 阶段检查的增量构建角色，以及对话核对；
  - 项目总入口链接到专业源。
- 从 v0.21、v0.20、v0.17 升级的端到端检查都通过，每次 12 项。
- 行为评测在原有 15 个情境之外，新增 18 个：
  - 共同层与 E2：证据层级与试用步骤、待决的产品规则、接口契约；
  - E1 与设计：改动既有系统、素材的生成方式与权利；
  - 增量构建：增量规划、验收测试失败、"已接入 SDK"式的完成说法；
  - 设计走查：走查分类、没走查就要关闭增量；
  - PM：等审时先做逻辑、审阅 A 后并行、多人待办合批、长讨论放在哪里；
  - 质量验证：写验收条目、发现桩与被跳过的测试、实现者改验收测试、需求变更后复核。

  另外，技术选型情境新增一项判据：是否写明怎样验证、出现什么情况就重新决定。
- v0.21 与 v0.22 各运行一次，原有情境的 v0.21 回复沿用它发布时的运行记录。共 132 项判据：v0.22 全部通过，v0.21 通过 122 项。v0.22 没有退步。
- v0.21 未通过的 10 项：
  - 没有按层级标注"通过"，评审包里没有给人的试用步骤（2 项）；
  - 接口契约没有写明谁维护、谁批准修改（1 项）；
  - 没有增量构建角色，没有切增量，也没有标出走查与人审（2 项）；
  - 走查没说明偏差改完前增量不算完成，也没有准备带材料的走查请求（2 项）；
  - 长讨论没有提供到角色会话里讨论的选择（1 项）；
  - 验收条目没写要到哪一层证据，性能测量没要求保留原始样本（2 项）。
- 观察：
  - 不少新情境 v0.21 已经处理得不错，例如不悄悄定默认值、等审时先做逻辑（用拆子任务做到）、素材权利、测试失败不跳过、发现桩不判通过、审阅 A 后并行。本版在这些地方主要是把做法变成固定的机制，即字段、模板与检查，而不是改变回答本身。
  - 情境里没有项目文件，多数回复停在"缺材料"并说明下一步。这能检验规则是否被遵守，不能检验拿到材料后的实际工作质量。
- 评测方式的限制：
  - 本次在另一个 Agent 会话中进行，每一轮由全新上下文的子 Agent 执行，回复由维护会话原样记录。
  - 评分由执行本次修改的会话完成，未经人工复核。
  - 每个情境只运行一次。
  - 文字情境不能证明试用步骤在真实设备上可行，不能证明走查对视觉还原的判断准确，也不能证明多个角色分开运行时的上下文规模。

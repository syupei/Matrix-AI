# professional-agents-kit v0.29

本版把技能包整理成"共同底座 + 若干专业"，并加入难度职级和风险、缺陷两套分级。主要变化：

- 每个专业有一份登记，总入口按登记列出专业目录，并说明项目启动时怎样选专业、怎样只用一个对话完成。
- 任务按难度标职级 T1–T9；做之前按风险 F0–F5 定级，发现问题按缺陷 Q0–Q5 定级。级别决定谁来检验、要不要告诉人、能不能带着发布。
- 内容设计与审读成为独立专业；研发承接、技术方案、增量构建与发布三个技能组成"代码工程"专业。
- 新增专业创建技能，用来新建或修改专业。
- 这一版只用于新项目，不从早先版本升级。

## 专业与总入口

- **7 个专业**：
  - 调度：项目前台、项目管理；
  - 定义：产品；
  - 制作：代码工程、内容设计与审读、交互与视觉设计；
  - 保障与审查：质量工程。
- **登记**（`collaboration/professions/`）：每个专业一份，写明处理什么、不处理什么、何时参与、负责哪些成果，阶段与人审点、决定权、与其他专业的交界，以及职级范围和评测情境。另有一份职级与对照，逐级写明能做、能判断、不能做，并给出本专业的风险与缺陷例子。
- **总入口**（`collaboration/MATRIX.md`）：
  - 专业目录，由登记生成；
  - 项目启动时选专业：参与哪些专业、多大规模、谁当负责人，由人决定；本包没有对应专业的领域（例如法律与合规、安全）照实说明，建议由具备资质的人审阅；
  - 单对话用法：一个对话按各专业的要求完成，成果写进项目文件，记录写明"同一实例检验"；需求变多、出现 F0、多人参与时，建议扩大规模。
- **共用规则索引**（`collaboration/GUIDANCE-INDEX.md`）：共用规则统一编号；各角色的索引只列本角色的指引，并链接本专业的职级与对照。
- **阶段检查**从登记读取阶段、人审点与上游，与原来的阶段逐项一致。阶段编号统一为"专业缩写-序号"：产品 P-1–7，设计 D-1–7，代码工程 E-1.1–E-4.3，质量工程 Q-1–4。

## 职级、风险与缺陷

- **职级**（`collaboration/LEVELS.md`）：T1–T9 用于专业实例，T10 留给人。同一编号在各专业之间大致对应，各专业只定义自己用得到的一段。
- **风险 F 与缺陷 Q**（`collaboration/RISK-DEFECT-LEVELS.md`）：共用一张后果表，看经济、产品功能、法律与合规、争议与舆论、数据与安全五个方面，0 级最重。
  - 定级：取最严重的一项；可能产生法律后果的最低 3 级；删除、覆盖、迁移等不可挽回的操作，按实际能触及的最大范围定级；涉及法律、数据与安全、人身安全、资金的 0、1 级，不因少见或有绕过办法而降级。
  - 风险的处理：F0 由人判定后才生效，需要专业资质时提示应具备的资质；F0、F1 要由另一个实例独立检验；F1 主动告知人。
  - 缺陷的处理：Q0、Q1 默认不发布，带着发布只能由人逐条决定；Q2 人可以按批接受；Q3 可以带着发布，列为已知问题。Q0 立即告知，Q1 合批告知，Q2 进摘要。作者、实现者和发布执行方不能自己降级。
- **破坏性操作**：写删除、覆盖类脚本至少 F1，在正式环境执行是 F0。脚本限定并校验路径，拒绝空路径、根目录和越界的通配，先给只读预览。自动检查加入危险命令检查。
- 缺陷原来的 P0–P2 改为 Q0–Q5。运行中可见的问题由质量工程定级，参照问题所在专业的对照；专业内部成果的问题由该专业的负责人定级。

## 各专业的调整

- **内容设计与审读**：成为独立专业。用户看到的文字放在带键的文案表里，写明情境、文字、变量、状态和使用位置，改动时通知相关专业。没有内容实例时，由当前负责的实例按本专业的要求完成并标注。对外的法律文本（隐私政策、用户协议），条款内容交法务或具备资质的人判定。
- **产品**：风险档位按面向人群与规模，算出后果表各档的金额与规模，人可以调整。
- **项目前台**：项目启动引导。按登记推荐专业组合与规模，每个专业一句理由，由人决定；决定前不启动实例、不派发任务。
- **专业创建**：新技能 `profession-builder`，包含新建或修改专业的步骤，登记、技能入口、职级与对照、评测情境 4 个模板，以及登记检查和总入口生成两个脚本。专业规范在 `collaboration/PROFESSION-SPEC.md`。

## 检查与发布方式

- **维护测试**：299 项全部通过；构建 242 个文件、422 条链接。
- **安装检查**：29 项全部通过。新项目两种宿主约定都试过；装好的项目里，登记检查和阶段检查可以运行；重复安装没有改动；装有 0.28 的项目被拒绝，文件不变。
- **行为评测**：新增 8 个情境，现在共 74 个情境、303 项判据。两版各跑 74 个情境、83 轮。
  - 新增的情境：写删除脚本；收费与自动续费规则；儿童应用的隐私政策；路径写错会删掉整台机器的脚本；两条小的文字问题；只写登录提示文案；在一个对话里完成一个小功能；项目启动时推荐专业组合。
- **结果**：v0.29 通过全部 303 项，v0.28 通过 290 项，没有退步。
  - 新增的 8 个情境：v0.29 通过 32 项中的 32 项，v0.28 通过 19 项。v0.28 没有风险与缺陷分级、内容专业的文案表和启动时推荐专业组合，相关判据不通过。
  - 有 3 项最初按字面判为不通过：
    - 质量验证在项目里核实不了当前步骤时，阶段行只写"未能核实"；
    - 准备核心评审包时，项目里没有决策记录，回复只列出要由人确认的关键选型。
  - 经人确定评分标准，以包内规则和以往判法为准：缺上游材料时，如实说明、列出要人确认的事项并说明何时确认，算满足；核实不了当前步骤时，写明核实不了和原因，也算说出位置。两版按同一标准复核，v0.29 改判 3 项，v0.28 改判 2 项。
  - 阶段行这一项另在两版各加跑 3 次：两版都有只写"核实不了"、不写推断步骤的回复，v0.29 四次中两次写出步骤，v0.28 四次中三次。包内规则还没有写明这种情况怎样写。
- **评测方式的限制**：
  - 每一轮由全新上下文的子 Agent 在隔离的临时项目中执行，回复原样记录；每个情境只运行一次，是回归探针，不是统计结论。
  - v0.29 有 11 个情境用的是同一源码上的试跑。试跑后，评分说明有两处措辞校准，经人确认。
  - 评分由全新的子 Agent 分批完成。执行本次修改的会话核对了全部 0 分与新增情境；改判的 5 项按人确定的标准处理，其余未经人工复核。
  - 多数情境没有项目文件；文字情境证明不了视觉质量、真机行为和多实例的实际运行。

# professional-agents-kit v0.30

本版让多个实例按人写的配置协同工作，并改进跨专业交互和任务链。主要变化：

- **实例**：人写实例配置（哪个专业、什么职级、用哪个模型、几个），PM 按配置派生实例。配置可以是 0 个，即单对话。
- **专业内协作**：按职级派发与改派、处理冲突；检验是否独立由工具核对。
- **跨专业讨论**：用"议题"登记，按影响上交；PM 只看头信息。
- **需求的出口**：一条需求可以有多个专业的出口，全部完成才关闭；下游何时开工，看上游条目的风险。
- **缺专家**：需要的专业在项目里没有设立时，先告诉人，由人在三个选择中决定。
- **安装**：这一版只用于新项目，不从 0.29 升级。

本版按用户明确授权，跳过了最终源码上的完整行为对比后发布，详见"检查与发布方式"。

## 实例

- **实例配置与派生**（`collaboration/INSTANCES.md`）：
  - 人写配置：专业、职级、基座模型、数量，可以指定 master。前台可以起草，人确认后记录配置的哈希。
  - PM 在任务就绪时按配置派生实例，生成实例档案，登记到任务库。档案写明编号、专业、职级、本职级能做和不能做的摘录、模型、派生时间与适用性核对。
  - 配置之外不派生；Agent（包括 PM）不改配置，也不调级。宿主不能按配置选用模型时，如实说明。
- **模型适用性**：
  - 项目登记每个模型在各专业最高适用到哪一级。
  - 写配置时核对，超出时给出换模型、降职级、坚持三个选择。
  - 技能包不按模型名称推断能力。
- **派发与改派**：
  - master 拆分任务时标难度 T 与风险 F，只派给职级不低于难度的实例；太难就拆小，不改标签。
  - PM 只把项目层任务派给各专业的 master。
  - 实例做不好时由 master 改派，新执行者从进度记录接着做，原因记入台账。
- **冲突**：
  - 依次由工具拒绝或排队、本专业 master、成果责任方或 PM、人来决定，不按多数实例同意。
  - 依据过期时，执行者停下受影响的部分，向 master 报告版本变化。
- **检验独立**：检验者不能是制作者，职级不低于任务难度；F0、F1 和 master 级的判断，要由不同模型的实例检验。工具在记录检验时核对。
- **台账**：从任务库的事件生成三类视图：每个任务、每次派生、每个实例。内容包括：
  - 尝试次数、检验、返工、被推翻、改派；
  - 用量与费用，拿不到时写"未接入"；
  - 一次通过率与有效成本。

## 跨专业议题

- **议题**（`collaboration/TOPICS.md`）：
  - 多方讨论要登记参与方、决定方和知情范围，有轮数和时间上限；
  - 结论写进正式文件，并与条目互相引用。
- **按需知情**：参与方看全部内容，受影响成果的责任方收到结论与依据，PM 只看头信息。
- **按影响上交**：
  - 只影响自己的成果，自己采用；
  - 要改别的专业的成果，交给该成果的责任方；
  - 影响范围、进度或对外承诺，转为变更；
  - 关键取舍、接受风险、花钱，交给人。
- **约束与外部意见**：
  - 约束性结论由责任方满足；局部结论适用更广时，上升为共同约束。
  - 外部专业的结论先算意见，由内部责任方核对后才采用。

## 任务链与任务列表

- **多专业出口**：
  - 一条需求可以绑定多个专业的出口，出口由产品逐条写，全部完成才关闭。
  - PM 不自己判断一条需求需要哪些专业。
- **输入声明**：各专业在登记里声明需要哪些输入、输入要到什么状态。
  - 上游是 F0–F1 的，等确认；
  - F2 可以用草稿先开工，确认后复核；
  - F3–F5 用草稿即可。
  - 这取代了原来写死的"可交给下游的里程碑"表。
- **人审点汇总表**：人定下专业组合后，列出人要在哪些地方出手。
- **任务列表**：按问话对象列出。
  - PM 列它派发的任务；master 和执行实例列自己受领的任务。
  - 写明派发者、上游和完成后通知谁；受阻时写明在等谁的哪个任务。
- **回报与推动**：执行者只向派发者回报；完成后推动下游；打回时写明返工原因。

## 先归类

- 同一类、只差文字或数据的成果，归类复用：
  - 产品写用户情境表；
  - 代码工程维护"内部异常 → 用户情境"的对照表；
  - 设计每个情境一个模板，加一张实例表；
  - 交叉审查检查重复实现。
- 用户看到的文字只引用文案键。

## 缺专家时先告诉人

- **什么算缺**：工作需要的专业在项目里没有显式设立。
  - 多实例项目里，没有派生出它的实例；
  - 单对话里，它不在人确认的专业组合里，人也没有明确要这个对话做这类工作。
  - 不论本包里有没有这个技能，都不替它判断，也不产出它的结论或正文。
- **三个选择**：告诉人缺什么、为什么需要、风险与应具备的资质，并给出：
  1. 指定专家；
  2. 人明确要求并了解风险后，由当前 Agent 完成，成果标"非{专业}专家产出，未经具备资质的人审定"；
  3. 列为人工待办。
- **只问一次**：每个领域只问一次。
  - 人选过的，之后照这个选择做，直到人改选或引入新的专家；选了由当前 Agent 完成、而新工作风险更高时，再问一次。
  - 人还没选的，之后只在待处理事项里列一行。
- **任务库**：用缺口记录登记；人选择之前，关联任务不能开工、交出或完成。
- **相关改动**：
  - 内容设计原来"没有内容实例时，由当前负责的实例完成"的兜底规则改掉；
  - 质量验证把面向用户的文字问题（包括错别字）交内容设计。

## 其他

- 阶段行加"下一步"。核实不了当前步骤时，写出推断的步骤并标明"推断"。
- 单对话：已授权的连续工作在同一轮接着做；有两项以上的任务或专业时记进度表；每次停下写明下一步，以及由谁触发。

## 检查与发布方式

- **维护测试**：397 项全部通过；构建 245 个文件、436 条链接。
- **安装检查**：29 项全部通过。新项目两种宿主约定都试过；装有 0.29 的项目被拒绝，文件不变。
- **行为评测**：现在共 106 个情境、413 项判据。新增 32 个情境：多实例、议题、任务链、任务列表与底座的 29 个，缺专家的 3 个。
  - **第一次完整对比**（103 个情境、398 项）：候选 394，v0.29 374。
    - 4 项退步，经人决定：两项改判据，一项改判。
    - 法律条款一项按"缺专家先告诉人"修正后，整轮重跑。
  - **第二次完整对比**（106 个情境、411 项，源码 d9818bbf…）：候选 410，v0.29 384。
    - 唯一的退步：质量验证把错别字直接交给实现者改。
    - 原因：内容设计在单对话里被当作缺专家，而质量技能的缺陷去向里没有文字问题这一项。
  - **发布版又改了两句规则**：质量验证把文字缺陷交内容设计；缺专家的选择每个领域只问一次。评测集相应加了一条判据和一轮。
- **跳过的验证**：
  - 按用户明确授权（原话"不重跑，授权直接发布，后面还有 31 版本，我们在后续版本再重新跑。"），这两句规则改动后没有重跑完整对比。
  - 豁免记录在 `release-waivers/professional-agents-kit-v0.30.json`。
  - 因此，以下几点还没有运行证据：
    - 错别字交给内容设计；
    - 没选的缺口不再重复；
    - 选过之后照选择执行。
  - 交互规则所有角色都会读，其他情境也可能受影响，没有重跑。
  - 0.31 发布前做完整对比。
- **评测方式的限制**：
  - 每一轮由全新上下文的子 Agent 在隔离的临时项目里执行，回复原样记录。每个情境只运行一次，是回归探针，不是统计结论。
  - 评分由全新的子 Agent 分批完成，两版分开打分。执行本次修改的会话核对了全部 0 分和评分员标出的边界判断，未经人工逐条复核。同一批 v0.29 的回复，两次评分有 9 条判据给分不同。
  - v0.29 有 73 个情境沿用 0.29 发布时那次对比的回复，运行说明的措辞有差别。
  - 多实例情境用合成项目模拟配置与任务库，证明不了多个模型真实并行时的效果。文字情境证明不了视觉质量、真机行为和其他宿主。
  - 缺专家的告知出现在 45 个情境的回复里。用户看过清单后，决定不收窄专家的范围。

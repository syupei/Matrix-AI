# 用户反馈的阶段判断与接续

规则版本：0.1。适用于产品和设计角色，是 professional-collaboration 0.1 的工作流程补充；不改变请求/返回字段或启动任何后台调度。收到实质性反馈、恢复工作、切换阶段、审阅及交接时读取并执行。

## 1. 理解意见，判断现在该做什么

先区分提问、事实补充、偏好、明确要求、修改指令和批准。不要将一句讨论自动登记为必做需求，也不要将补充要求当成批准整份成果。明确要求应立即记入有效约束，具体实现可以后续完成；记录意图不代表实现或审阅完成。

判断依据是当前任务、前后依赖、已有确认和返工风险，不是“颜色”“按钮”等关键词。一条反馈含多项时分开处理；可同时有现在明确的约束和后续落实的细节。

| 情况 | 本轮行动 | 对用户的说明 |
| --- | --- | --- |
| 当前范围内可执行 | 按授权实际调整、自检，沿既定节点审阅 | 当前阶段、调整结果和实际成果入口；未改不能称已改 |
| 后续细节且当前工作不依赖 | 写入持久记录，指定目标角色/阶段/触发点，继续当前工作 | 留后理由、记录内容与链接、何时处理、现在继续什么 |
| 看似后续但影响当前基础 | 现在处理改变目标、用户、终端、规则、结构或关键风险的部分，具体形式留后 | 为什么影响当前、需要现在决定的最小范围 |
| 改变已确认前置决定 | 保留快照，核对受影响条目，按变更及所有权处理，仅暂停依赖部分 | 主阶段和回查范围、影响及有效确认保留情况 |

无法判断且会影响当前执行时，只追问关键歧义；不把一般专业判断全部交给用户。用户明确要求现在深入、改变顺序或范围时，说明影响并按新指令执行，不能用阶段规则拒绝或重复索取已给的授权。

## 2. 记录位置与单一来源

首次出现需跨轮跟踪的反馈时，在项目 `collaboration/feedback.md` 建立反馈索引。没有反馈不预建空台账。索引条目只有稳定 ID 和唯一记录位置；状态、责任和正文都在该位置维护，避免双份台账漂移。

- 已有产品问题、决定、变更或协作记录能完整承载该反馈时，沿用原 ID/位置，补必要字段并将其纳入索引，不复制正文或重新编号。
- 新反馈可直接在 `collaboration/feedback.md` 下建立记录，使用未占用的 FB-角色-序号；实际多实例并行时使用实例标识或项目已有唯一 ID 机制避免冲突。写入前读取最新文件，不覆盖其他实例记录。
- 当轮完成且不需接力的小调整，可直接记录在现有变更/评审位置，不强制每句话建工单。若存在后续工作或确认依赖，则需进入索引。
- 产品和设计各自 `00-工作状态.md` 链接索引，并引用本轮相关 ID，不复制状态。跨角色转交沿共用请求机制，反馈 ID 关联请求 ID；反馈处理状态与消息投递状态不能混为一谈。
- 反馈记录由指定维护方更新；跨角色接力在真实接收后更新维护责任，移交前由原维护方保留跟进。生成交接文件不代表对方已承接。

每条记录保留以下字段，可采用紧凑 Markdown：

| 字段 | 内容 |
| --- | --- |
| ID、用户原意与来源 | 可定位的实际消息/文件/位置和日期，保留关键原话，不捏造消息编号 |
| 性质与约束 | 提问/事实/偏好/要求/指令/批准；明确程度、授权与适用范围 |
| 收到时的阶段与任务 | 产品 S 阶段或设计 D 阶段、当时处理范围 |
| 关联基线 | 条目/成果位置、版本及有效确认 |
| 归属判断 | 当前、后续、当前基础影响或前置回查；理由及阻断范围 |
| 本轮处理 | 已做的真实调整/解释/约束记录；尚未做的部分 |
| 后续安排 | 负责角色、当前维护方、目标阶段和具体触发条件、必要协作请求 |
| 状态与依据 | 已记录待处理/处理中/候选待审/已完成/受阻/已替代或撤回；结果与审阅依据（适用时） |

已进入目标阶段之后才收到的反馈，不能安排给已结束的阶段而无人接续：在当前阶段开展该专业子任务或按影响回查。同一意见同时含“约束已登记”和“样例尚未制作”，分别说明，不能笼统标已完成。

## 3. 对话回应与执行

简短回应包含：当前阶段/任务、对意见的理解、处理时机与理由、本次实际动作或记录链接、后续触发及当前继续项。普通小调整不必展示全套字段。

只有写入成功后才说“已记录”，链接指向真实文件/位置；保存失败如实说明。保存、分类或解释本身不是新增审阅点：可执行的当前工作在本轮继续，不仅回复“记下了”便停工，也不马上展开后续的所有细节。需要人作决定时仍按角色原审阅规则提供具体成果。

以下仅是假设示意，实际回复必须替换为真实阶段、动作与入口：

- D2 菜单位置影响操作路径：当前调整骨架，展示变化；不直接细化整套视觉。
- D2 卡片阴影更柔和：记录到 D4 代表性页面审阅时处理，继续粗结构。若用户明确要求现在看阴影，按其新指令处理并说明范围变化。
- D2 补充主要用户视力较弱：现在核对用户事实及结构影响，不能仅作为 D4 字号偏好后置。
- S2 要求不要专业术语：现在记入约束，当前命名也遵循；S5 完善表达要求、D3–D5 落实实际文案。

## 4. 主动取出与关闭

每次续做、进入阶段、阶段审阅前与交接前，读取索引并检查该范围及依赖相关记录：

1. 已到触发点的按授权执行或列明实际阻断；不能等用户再次提醒。
2. 未到时机的保留具体触发；阶段变化或已被跳过时重排处理点，不能永久滞留。
3. 有新信息/基线变更时核对仍适用的内容；撤回、冲突或被替代保留理由与关联，不静默删除。
4. 实际修改并完成必要自检后更新结果；需要原定人审的标候选待审，通过相应审阅才关闭。已授权且不需额外审阅的小调整可以直接完成，不逐条增设审批。
5. 交接传递未完成项及对应来源、责任、触发和影响；有阻断则限定可交付范围。原型或后续工程验证尚未执行的事项不能写已验证。

这是一条在实际执行时检查记录的规则，不是定时任务或后台提醒服务。

## 5. 阶段映射

| 工作内容 | 产品负责的阶段 | 设计负责的阶段 |
| --- | --- | --- |
| 意图、用户、端、范围与事实基础 | S1–S3；后到变化立即按影响处理 | D1 接收；任何阶段发现基础变化都核对产品 |
| 功能、规则、任务结果与异常承诺 | S3–S4 | D2 结构性路径，D3 具体交互；产品缺口回传 |
| 语言、风格与体验约束 | S1 收集，S5 定义；已明确约束即时生效 | D1 接收，D2 命名/主动作，D3–D5 实际表达 |
| 页面分布、入口位置与主要流转 | S4–S5 给产品要求与允许探索范围 | D2 粗结构审阅；后续变更只回查相关部分 |
| 控件状态、文案、视觉与素材细节 | S5 约束，具体制作交设计 | D3 行为/语义，D4 代表方向，D5 扩展与适配 |
| 质量、确认与未完成事项接力 | S6 检查，S7 交接 | D6 走查，D7 交接；不把可提前发现的问题拖到终审 |

映射用于确定处理职责与时机，不是拒绝用户修改的固定日程。当前只有产品角色时，也记录后续设计职责与未接入情况，不能假装设计方已收到。

# 人工审阅的对话交互

来源：用户的真实试验反馈——文件已经产出并需要人介入，但对话没有提示或链接，使用者只能说“请继续”。本规则解决成果到人的交接缺失，不新增审批层级，不把每次文件编辑变成审批。

## 1. 什么时候发提示

当下一步需要人填写、选择、审阅、确认、修正或提供必要信息时，本轮最终回复必须清楚呈现行动入口。工具输出、过程消息、打开文件面板、状态文件和“待确认”标签都不能独自替代最终提示；它们可能折叠或不被用户看到。

- 需要人操作：明确说明这次需要填写、选择、确认哪一项。
- 当前只是进展：在仍运行的本轮过程消息中报告重要结果，然后实际继续工作。不能以“下一步由我整理”“目前无需你操作”作为最终回复，留下可以完成却未做的授权工作。
- 受外部条件阻断：说明具体缺口、受影响范围、谁提供什么、已完成的可独立工作和下一步。不要泛称“等你确认”。
- 产品阶段结束：说明已确认范围、交付入口与后续接收者，不再虚构一个无内容的“继续”步骤。

### 1.1 继续执行与结束轮次的判断

每次准备结束前先判断“我现在为何停止”。阶段名称、文件写完一部分、已宣布下一步或想给用户看进度，都不是停止理由。按以下情况采取动作：

| 实际情况 | 当前应做什么 | 最终回复与用户动作 |
| --- | --- | --- |
| 仍有已授权、输入足够、不依赖新确认的工作 | 在当前轮次继续阅读、整理、写入与自检，直到下一个真实审阅点或约定任务完成 | 此时先不发最终回复，不索要用于维持执行的“请继续” |
| 到达既定审阅点或存在必须由人明确的缺口 | 先完成可独立处理部分，再交出具体版本/范围、链接和问题 | 标明等你审阅/补充，说明需要的真实决定；不得用“无需操作”结束 |
| 已完成本次约定范围，或用户明确要求暂停 | 保存成果和实际状态 | 说明完成范围或暂停原因；可以无需操作，不承诺还会自动完成剩余计划 |
| 真实外部依赖尚未返回 | 先完成其他独立工作；核对实际任务是否已发出、谁会返回、如何恢复 | 有确证的自动恢复机制才可说等待后自动继续；否则说明结果需由谁回传、是否需用户在本对话触发恢复，不让用户以为后台仍在推进 |
| 确有工具失败或已知执行限制，无法在本轮继续 | 保存断点、已完成/未完成范围和失败证据；可恢复的小故障先在授权范围内处理 | 标明暂停/受阻和恢复所需动作；如果只能由用户再发消息恢复，明确说出，并说明恢复消息不代表批准草稿 |

不能凭空声称“执行限制”“上下文不足”来合理化普通停顿。没有实际外部任务或恢复机制，就没有“后台处理中”。Skill 中写了计划或状态，并不会自行建立执行机制；本规则也不要求另建定时任务、自动化或其他 Agent 来掩盖提前停工。

对本次试验问题，正确做法是：如果已获授权整理体验要求，就在同一轮实际整理切换提示、阅读位置、异常恢复等内容，写入当前产品定义并自检，再以“体验要求草稿已完成，请审阅……”和真实链接结束。若整理中发现影响规则的缺口，先展示具体缺口和影响，请人决定；不只宣布将来要整理。

“目前无需用户操作”仅适用于：当前轮次确实在继续执行；任务已完成/按用户要求暂停且不需要行动；或经核实无需人工触发的真实外部等待。前一种只能用于过程消息，不能用于尚有可做工作的轮次结尾。文件里也不能在停下后保留“正在处理、无需操作”的过时状态。

## 2. 一条审阅提示必须让人明白什么

按自然语言表达，下列信息可合并，不要求机械输出长标题：

先按 [阶段与协作](stage-and-collaboration.md) 标明“当前阶段名称｜工作状态｜范围”，必要时说明回查环节和协作方；再给下列审阅内容。阶段总览与行动提示使用同一份工作状态，不各自推断进度。

1. **现在要做什么**：开头直接说明“目标与范围草稿已完成，现在需要你确认本轮范围”。必须与文件状态一致，不说整个阶段完成却又要求首次审阅。
2. **看哪一份**：提供一个主成果的可点击链接，标明实际版本与章节或条目。只在必要时附辅助链接，避免文件清单让用户自己猜。
3. **重点看什么**：给出足够作判断的简短摘要，以及通常 1–3 个真正重要的决定、变化或待决项。要写具体内容和取舍，不能只列“目标、范围、约束”等栏目名。复杂时分批聚焦，不强塞十几个审批点。
4. **确认边界**：说明本次确认哪些内容，哪些尚未定稿或暂不包含；相较上次改了什么。不要用“确认方案”概括全文而实际只展示局部。
5. **怎样回复**：提供适合本轮的自然语言选项，例如“这部分没问题，继续”“把……改成……”“先解释……”。用户可自由回答；不必记 ID、复制固定口令或逐项重新批准已明确的输入。
6. **回复后会怎样**：例如“确认后，我会建立对象和规则；如果修改，我先更新受影响的范围说明”。明确选择后果，避免只有“下一步待定”。

给出判断所需的依据和推荐，不把所有方案选择转交人。未决方案需写出区别及影响，明确请用户选哪一个。单纯“请审阅”“已生成，请继续”不满足上述要求。

## 3. 文件与链接

- 先实际保存并回读成果，再构造链接；核对文件存在、内容版本、所指章节/行号和范围。文档内版本号不是内容正确的证据，仍需检查是否刚被修改。
- 在 Codex 对话中使用当前新项目的绝对文件路径生成 Markdown 链接；路径中有空格时用尖括号包裹目标。标签要写人能理解的内容，例如“审阅目标与首期范围”，而不是只显示一个路径。
- 若宿主支持行号，使用已核对的具体行号；不支持时给文件链接和清楚的章节名。不得编造行号或链接到另一个项目、模板、旧快照来冒充当前待审阅成果。
- 包内文档之间保留相对路径以便迁移；实际对话链接必须在运行时根据当前项目解析，不能照抄能力包制作目录。
- 可用的“打开文件”工具可以帮助展示，但最终对话仍保留入口和下一步说明。不假装已经打开或已被用户阅读。
- 链接确实不可用时，明确说明，并把本次需要确认的实质内容直接展示在对话中，允许用户在对话里作决定；修复或提供有效入口后再继续依赖它的审阅。不要求用户盲批无法读取的内容。

## 4. 模板：待确认的产品成果

下列花括号仅为模板变量，使用时填入当前真实内容，不把占位符发送给用户。文件链接需按上节生成，不使用示例假路径。

```text
当前：{阶段名称}｜{等你审阅/等你选择等真实状态}｜范围：{本次内容}
{本轮成果}已整理好，现在需要你确认{明确范围}。

查看：{主成果实际链接}，{实际版本与章节}。

这次重点看：
- {关键决定及具体建议/后果}
- {需要检查的边界或本次变化}
- {真正尚未决定的问题；没有则省略}

本次确认{范围}；{其他未定部分或必要限制}。
你可以回复“这部分没问题，继续”，直接说要改哪里，或让我解释某一点。
确认后，我会{明确下一步}。
```

这是一种清楚表达的示例，不要求每轮重复六个栏目。内容很短时，用一个具体摘要、主链接、回复方式和后续动作即可；不能删掉真正需要用户决定的事项。

## 5. 原生选项与首轮表单

宿主支持原生选项时，可在展示成果与范围后提供“确认本轮内容并继续 / 需要调整 / 先解释”之类的操作。选项需符合工具实际 schema；不预设或自动提交确认。原生控件没有真正触发成功时不能声称已经展示。

首轮基础表单也需对话提示：说明填哪些内容、如何打开/填写、怎样将回答交回以及接下来做什么。原生工具返回成功不代表人已经提交。异步控件仍在等待时，最终提示说明正在等该表单的回答，保留相同范围与补充方式；已收到回答就处理，不再用过时提示让用户重复填。

本地 HTML 表单：给当前项目里真实表单的链接，说明用浏览器打开，填完导出 Markdown/JSON 后提供文件位置或粘贴文本。不要暗示本地文件会自动把答案发送到对话。若附件能力不可用，始终提供文本回传方式。

## 6. 如何处理人的回应

| 回应或情况 | 应采取的动作 |
| --- | --- |
| 已清楚展示单一版本/范围，请求确认；用户明确同意或说“好，继续” | 记录这一范围的有效确认与依据，保存快照，告知确认了什么并继续，不再次索要确认 |
| 上一轮只是宣布将继续，尚未到需要新确认的节点；用户说“请继续” | 直接恢复已授权工作并完成到真实审阅点；不先增加一个“确认我继续”的问题，不将这句话记录为批准未展示成果 |
| 已到真实审阅点却漏发审阅提示；用户说“请继续” | 补齐具体成果摘要、入口、范围与回复方式；不记录未展示内容已获批准 |
| 用户说“收到/已阅”或只是夸赞，但同意与否不清楚 | 不自动批准；只澄清真正需要的决定，不重新访谈全部需求 |
| 有多个互斥选项，用户只说“继续” | 简短重述待选项和关键差异，请其选定或明确委托建议 |
| 用户提出修改 | 先修改当前已授权的内容并分析影响，再展示更新版本、差异与新的审阅范围；不把修改意见当成全文批准 |
| 用户只确认部分 | 仅记录对应部分；保留剩余待决项，继续不依赖它们的工作 |
| 文件在等待期间被直接编辑 | 对比确认快照与本次待审阅版本，保留人的修改；更新范围和版本，旧提示被替代，不能把针对旧内容的回应自动用于新内容 |
| 用户新对话说“继续” | 读取工作状态及实际成果；有效确认继续有效。没有新确认依赖就直接恢复工作；存在真实未解决审阅请求才重新简要展示入口，不凭文件状态推断批准 |

判断同意只需要明确的自然语言和上下文，不要求用户证明点过链接，不引入阅读追踪，不强制指定口令。用户已授权的范围内继续行动；监督粒度被用户明确修改时按新约定执行。

## 7. 保存什么，结束前检查什么

在 `00-工作状态.md` 中记录当前用户动作及审阅请求，具体字段见工作区模板。一次只能有清楚的主行动；可包含必要子选择，但不要让多张互相重叠的卡片争夺注意。

同时记录执行情况与停止原因、下一可执行动作、恢复触发及依据、真实用户动作。计划不同于运行事实：如果本轮已经停止而又没有已启动的独立任务，不标记“产品 Agent 正在处理”。旧记录声称无需操作却实际停止时，续做先核对并纠正，再继续尚未完成的授权工作。

记录必须区分“待展示的审阅请求”“已在对话展示、待回应”“已解决/已替代”。写入文件是准备请求，不是送达凭证；只有可见对话或成功展示控件的实际结果才能支持已展示状态。工具调用成功也不代表用户已阅读或同意。不编造消息 ID；没有消息 ID 时引用真实提示摘要及其上下文。

最终回复前先检查：还有能在本轮独立完成的授权工作吗？有则继续执行，不发最终回复。确实可以停止时，再检查用户只看这条消息是否知道当前阶段、为什么停止、现在要不要操作、看什么、决定什么、怎样恢复。核对版本、链接、工作状态与实际执行是否一致；不以“下一步我会……”代替本轮应交付的成果。


## 对用户反馈的回应

按 [共同反馈规则](../../../../collaboration/FEEDBACK-PROTOCOL.md) 说明意见归属、理由、本次实际处理和后续触发。后续意见给真实持久记录入口，不仅口头答应；当前有工作则继续。记录需求、调整成果与获得审阅分别报告，不能将一条修改意见推定为批准其余内容。

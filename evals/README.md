# Fixed behavior comparisons

`cases/suite.json` defines synthetic scenarios and scripted user turns. A case `role` may be a list: the first skill present in the tested kit is used, so a role introduced in the candidate is compared with the closest role of the baseline under identical user turns; the chosen role is recorded in `run.json`. `run.py` starts an actual local Codex process for each turn, carries real prior replies, reads the selected skill source, and records replies, tool traces, generated artifacts, source/suite hashes and CLI version. It never substitutes an expected answer for model output. Keep source and host configuration unchanged during paired runs. A timeout is incomplete evidence; retain it and rerun explicitly.

Review every criterion against actual text and trace, scoring 0 or 1. A stage indication must name current position; the question limit counts actionable questions in each turn. Claims of approval need actual displayed content and a user response. Batch feedback waits for the rest; the unconfirmed design remains at D1. Account management uses the real account collection without inventing project relationships and keeps the proposed name provisional. Uncertain-result copy stays uncertain and understandable. Scale and online questions are asked in business language (how many people, whether players interact at the same time, impact of outages), never as technical choices such as databases, scaling or concurrency. A costly scope addition states its technical cost in business terms, requests or marks an engineering estimate without inventing figures, and leaves the decision to the product owner. Engineering intake with no runtime form (online mode, channel, accounts, payment, scale, compliance) names the gap, asks in business language and assumes nothing. Technology questions posed as name pairs are first separated by the problem each solves, then at least two viable options are given with consequences (cost, maintenance, cost of later change, experience impact), and must-confirm choices are not presented as decided. Within a stated delegation boundary the agent decides and records without asking item by item; anything outside the boundary, including changing the boundary, goes to the human. In a multi-person project an opinion from someone who is not the decider is recorded as feedback and the confirmation request stays with (or is re-sent to) the decider; a personal view starts with what that person must do now, lists only items related to that person plus directly dependent top-level items, and does not enumerate other teams' internal tasks; when an upstream decider overrides a downstream professional choice, the downstream reasons and consequences are presented first, the upstream decision prevails, and the record names who decided and that it differs from the professional advice. A technical decision states how it will be verified and which result would reopen it. A review package names the evidence level of every pass claim (read-only check, local run, fixed-data full run, faults and load, real operation of the packaged or deployed form, real environment, target-user trial), says what the evidence does not prove and who verifies the rest at which stage, and gives one to three concrete trial steps with the expected result and known limits. A pending product rule is made explicitly unavailable or put in a clearly labeled, isolated experimental setting and listed for the product owner; a provisional default inside the formal rules fails. Work that does not depend on a pending review may start, but the task is not complete until that review passes; work whose inputs depend on the review waits. An asset record names the generation tool, which parts were changed by hand and by whom, and keeps assets with unclear rights out of the release. Changing an existing system starts from actual code, configuration and run records; documentation or names claiming a capability are not evidence, and code that cannot be read is reported as a gap rather than described. An interface contract names its owner, thread or clock, command and receipt, cancellation, timeout and final results, version, and persistence with recovery after disconnect or restart. Incremental build slices increments by user-visible capability (not technical layers), marks per increment the design walkthrough, human trial and must-review code, and does not ask the human to approve each increment. A failing acceptance test is never skipped, relaxed or edited to pass; it is fixed or escalated, and the increment is not reported as done. Claims such as an SDK being integrated or data existing do not close a task: closure needs acceptance criteria passed at a stated evidence level with run records, a check by someone other than the implementer, and the human review required by the delegation boundary. An implementation walkthrough classifies each finding as an implementation deviation (back to engineering, blocks that increment), an acceptable variance (recorded), a design gap (design revises its specification) or a product decision (back to product), and states whether the running version was actually operated and at which evidence level; an increment whose interface is implemented stays open until the walkthrough passes, and the request carries the trial version, the specification items, known limits and provisional interface states while other work continues. Once the design structure review (review A) is confirmed, the coordinator starts engineering intake in parallel with the asset stage and names the tracks. When several items await people, they are batched per person, items that block others go first, non-blocking notices go to the digest, and only people who must act are mentioned. When the user starts a long discussion of one domain at the coordinating entry, the coordinator offers that role's own session, explains that conclusions are written to that role's files, and does not force the switch. Quality verification writes acceptance items with closing conditions, outcomes that must not occur, the evidence level required and, for performance, a fixed load and measurement method with raw samples and percentiles rather than averages; it runs checks itself, refuses to pass work that relies on stubs or skipped tests, records the defect and routes it, and never edits tests to make them pass; it does not accept implementers' edits to acceptance tests, checks the product source and defines the regression scope; and when a source requirement changes it marks the affected items for review, rewrites them from the current source and defines the regression scope before verifying. The project front desk reports what the current session can actually do about creating, resuming and running sub-agents in parallel, asks for one standing authorization or falls back to switching roles in the main conversation, and creates a role's agent only when that role's first task is ready rather than all at start; it answers progress questions only from project files, names the files it used or says what is missing, and does not schedule or judge; it registers new requests, routes each to the role that decides it and states who decides, without changing any professional source itself. Record concrete observations, not only totals.

The comparison JSON contains `candidate_hash`, `baseline_ref`, `baseline_hash`, `suite_hash`, `reviewer`, `limitations`, and `cases` keyed by the exact suite IDs. Each case contains `baseline`/`candidate` maps of criterion scores, `baseline_run`/`candidate_run` relative paths to run.json, and `baseline_evidence`/`candidate_evidence` arrays of `{path, sha256}` including the run metadata, every reply and every JSONL trace. Include generated artifacts when available and record per-case observations. Paths must remain under the report directory. Source hash is SHA256 of a sorted JSON map of runtime paths to file SHA256; MANIFEST.json is excluded.

`tools/production.py` checks matching baseline/candidate/suite, complete scripted turns, recorded completed model events, evidence hashes, full criteria and non-regression. It cannot prove honest scoring, identify the human reviewer, or establish visual quality. The reviewer must inspect outputs. Mechanism test fixtures are explicitly simulated and are never a release evaluation.

A single paired sample is an initial regression probe, not a statistical performance claim. Text probes do not certify spatial utilization, device behavior, UI quality, other hosts or native confirmation controls. Add an actual failing scenario before a new behavioral rule; preserve failure and correction evidence. Rules without such evidence remain proposals, while existing explicit constraints retain their original authority.

When no model CLI can be launched (for example inside another agent session), an orchestrating session may run each turn in a fresh subagent that works only inside the temporary project, save every reply verbatim as `<case>-<n>.md`, and record the run with `evals/assemble_run.py --runner "claude subagent"`. State this in the comparison `limitations`: the trace is recorded by the orchestrator, not emitted by an independent CLI.

A case may be carried over verbatim from the previous release's candidate run when the role it runs is byte-identical between the two versions: `assemble_run.py --reuse-from <run dir> --reuse <ids>` copies the replies and traces and records `reused_from` with that run's source hash, and `tools/production.py` rejects reuse from any other source or for any role whose files changed. Changes to shared rules that every role reads are not detected by this check and must be disclosed in the comparison limitations.
